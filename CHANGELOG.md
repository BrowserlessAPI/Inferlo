# Changelog

All notable changes are listed here. Inferlo follows [semantic versioning](https://semver.org); until 1.0, minor versions may include breaking changes, always listed under "Breaking".

## Unreleased

- Apollo Server: `new ApolloServer({ schema: graphqlSchema({ query, mutation }) })` with `context: async ({ req }) => graphqlContext(app, req)` (from `@browserlessapi/inferlo/graphql`) serves the app's GraphQL fields from Apollo Server 5, in its standalone server and in Express with `expressMiddleware` from `@as-integrations/express5`. Each field runs its route as the caller of the request, with the route's auth, permissions, validation, rate limits (per-IP limits use the socket address), tenant scope and audit; errors keep the route's `code` and `status`. Tested with `@apollo/server` 5.0.0 and the latest release, with `graphql` 16. See [Apollo Server](docs/graphql.md#apollo-server).

- Fix: response validation no longer flags answers of routes with `response: Model.row` (or `t.array(Model.row)`): the fields Inferlo sets (`id`, `createdAt`, `updatedAt`, `tenantId`) were checked with the rule for request bodies, which refuses them, and `null` in `.optional()` fields (rows have it for columns left out) was refused, so every such route logged IL2016, or answered 500 with `validateResponses: "error"`. Request bodies still refuse those fields. See [Response validation](docs/routes.md#response-validation).

- GraphQL Yoga: `createYoga({ schema: graphqlSchema({ query, mutation }), context: ({ request }) => graphqlContext(app, request) })` with `graphqlContext` from `@browserlessapi/inferlo/graphql` serves the app's GraphQL fields from GraphQL Yoga, with Yoga's plugins, subscriptions and GraphiQL page. Each field runs its route as the caller of the request (its Authorization header, API key or session cookie), with the route's auth, permissions, validation, rate limits, tenant scope and audit, as with `graphqlRoute()`. The request can be a Web `Request` or a Node.js request (whose socket address per-IP rate limits use). Invalid arguments raise the new IL6060; fields executed without the context still answer IL6059. Tested with `graphql-yoga` 5 (with `graphql` 16) and 6. See [GraphQL Yoga and other GraphQL servers](docs/graphql.md#graphql-yoga-and-other-graphql-servers).

- LlamaIndex.TS: `toLlamaIndexLLM(ai, { model, for })`, `toLlamaIndexEmbedding(ai, { model, for, batchSize })` and `toLlamaIndexTools(tools, { ai })` from the new entry point `@browserlessapi/inferlo/llamaindex` let LlamaIndex.TS agents, indexes, query engines and chat engines run on Inferlo's AI and use Inferlo tools. The LLM is a LlamaIndex `ToolCallLLM` whose `chat` and `complete` calls (streamed or not) go through the alias with its fallback models, budgets, usage tracking and tracing, on any provider Inferlo supports; tool calls come back in `options.toolCall` for LlamaIndex to run, usage and cost are in `raw.usage`, and images in user messages reach vision models. The embedding model is a `BaseEmbedding` that calls `ai.embed` once per batch. Inferlo function tools become LlamaIndex tools with Inferlo's validation; routes run as the signed-in user with a request's `ctx.ai` (IL5009 without it). `responseFormat`, audio, video and file content and invalid arguments raise the new IL5037. `@llamaindex/core` is a new optional peer dependency (0.6.0 and later) that the core package never loads; tested with LlamaIndex's `LLMAgent` on Node.js and Bun, and a new CI job tests 0.6.0 and the latest release. New exports `InferloLLM`, `InferloEmbedding` and the types `LlamaIndexLLMOptions` and `LlamaIndexEmbeddingOptions`. Docs in integrations.md ("LlamaIndex.TS"), errors.md and support.md, the AGENTS.md support table, the app template's AGENTS.md and the llamaindex-support benchmark task.

- GraphQL (part 2a): `app.describe()`, `inferlo describe` and OpenAPI list the fields of each `graphqlRoute()` endpoint and the routes behind them. The endpoint's `describe()` entry has `graphql: { query: { notes: "GET /notes" }, mutation: { createNote: "POST /notes" } }` (the versioned paths under `apiVersion()`), and each route that is a field has `graphqlFields: ["Query.notes"]`, so a change to a route shows its GraphQL callers. - GraphQL (part 1): `graphqlRoute({ query, mutation })` from the new entry point `@browserlessapi/inferlo/graphql` adds a `POST /graphql` endpoint whose fields are routes the app already has (`query: { notes: listNotes, note: getNote }, mutation: { createNote }`). Each field runs its route in the same process as the caller, so GraphQL clients get the route's auth, permissions, validation, rate limits, tenant scope and audit; there are no separate resolvers. Arguments are the route's params, query and body fields; types come from its `response` schema (object types for `t.object` and model rows, enums, lists, nullability; the `JSON` scalar without one). Route errors are GraphQL errors with the route's code, status and details in `extensions`; server errors say only "Internal error.". The endpoint is private by default (`auth`), with `rateLimit`, `introspection: false` to hide the schema, `maxFields` (default 20 top-level fields per request, more answer the new IL2020), and a 100,000 character and 10,000 token document limit. `graphqlSchema({ query, mutation })` returns the schema for `printSchema` and client code generation. Invalid options raise the new IL6059 at startup. `graphql` is a new optional peer dependency (16 and later) that the core package never loads; a new CI job tests graphql 16 and the latest release on Node.js and Bun. See [GraphQL](docs/graphql.md).

- OpenAI Agents SDK: `toOpenAIAgentsModel(ai, { model, for })` and `toOpenAIAgentsTools(tools, { ai })` from the new entry point `@browserlessapi/inferlo/openai-agents` let agents built with the OpenAI Agents SDK (`@openai/agents`) run on Inferlo's AI and use Inferlo tools. Docs in integrations.md, errors.md and support.md, the app template's AGENTS.md and the openai-agents-support benchmark task.

- Idempotency keys: `route.post(path, { idempotency: true })` (or `{ ttlMs, required }`, on POST, PUT, PATCH and DELETE routes) runs a request with an `Idempotency-Key` header once, so clients can safely retry payments, orders and other requests that must not happen twice. Repeats with the same key on the same route, from the same user, get the first answer (status, headers and body) with `Idempotent-Replayed: true` for `ttlMs` (default 24 hours, at most 30 days), without running the handler. A repeat while the first request still runs answers 409 IL2018, a key reused for a different body, query or path 422 IL2019, and with `required: true` a request without a key 400 IL2017. Errors and 5xx answers release the key; answers that set a cookie, event streams and bodies over 1 MB are not stored. Keys are claimed atomically in the app cache (memory, `database` with one `INSERT ... ON CONFLICT` statement, or `redis` with `SET NX`), so with a shared store a key runs once across every instance. The check runs after auth, permissions, rate limits and input validation. OpenAPI lists the `Idempotency-Key` header and the 409 answer; invalid options raise IL6058 at startup. New type `RouteIdempotency`. Docs in routes.md ("Idempotency keys"), security.md and errors.md, a rule in the app template's AGENTS.md, and the idempotent-notes benchmark task.

- BullMQ: `createApp({ jobQueue: { store: bullmqJobStore(queue, worker) } })` with `bullmqJobStore` from the new entry point `@browserlessapi/inferlo/bullmq` keeps Inferlo's jobs in an app's BullMQ queue, on the same Redis and in the same dashboards. Each Inferlo job is a BullMQ job (name and id are Inferlo's, `runAt` is the delay); Inferlo takes jobs with BullMQ's manual processing API from a `Worker` created with `autorun: false` and no processor, and runs them with its own handlers, so validation, retries with Inferlo's backoff (`moveToDelayed`), crons and events queued once, tracing, tenants, metrics and `onError` work as with the other stores. Running jobs keep their lock (extended every `lockDuration / 2`); a job whose process stopped is moved back by BullMQ's stalled-job check and runs again with `lastError` saying the worker stopped, or is failed without attempts left. Finished jobs are kept 7 days as `completed` or `failed`. Jobs in the queue that Inferlo did not queue are failed with a message. Invalid arguments raise the new IL6057. `jobQueue.store` now also takes a store object, `app.jobs.queue` and `describe().jobQueue` can be `"bullmq"`, and the types `JobStore` and `JobQueueName` are exported. BullMQ is not a dependency and is never imported by Inferlo; tested with BullMQ 5.0.0 on Redis 6.2 and the latest BullMQ on Redis 6.2 and the latest Redis, on Node.js, Bun and Deno, in a new CI job. Docs in jobs.md, integrations.md, errors.md and support.md, the app template's AGENTS.md and the bullmq-jobs benchmark task.

- Error tracking: `createApp({ onError: (error, info) => ... })` is called with every unexpected error after it is logged (5xx answers from handlers, middleware, database and AI calls and timeouts, failed WebSocket messages, and failed job attempts; never 4xx), redacted like log entries, with where it happened: `{ source: "request" | "websocket" | "job", requestId, method, path, route, userId, tenantId, traceId, spanId, job, jobId, attempt, maxAttempts, final }`. A hook that throws or rejects is logged and never changes the answer or the job. For Sentry, `onError: sentryOnError(Sentry)` from the new entry point `@browserlessapi/inferlo/sentry` captures each error with the tags `inferlo.source`, `inferlo.route`, `inferlo.job`, `inferlo.final`, `request_id`, `tenant_id` and `trace_id`, the user's id only (never the email), and an `inferlo` context; any Sentry SDK with `captureException` works (`@sentry/node`, `@sentry/bun`, `@sentry/deno`, `@sentry/cloudflare`). New types `ErrorInfo` and `OnError`, and codes IL6055 (`onError` is not a function) and IL6056 (`sentryOnError()` without a Sentry SDK). Sentry is not a dependency; tested with `@sentry/node` 9.0.0 and the latest on Node.js, Bun and Deno. Docs in observability.md, integrations.md, errors.md and support.md, the app template's AGENTS.md and the sentry-errors benchmark task.

- Events between services over RabbitMQ: `createApp({ name: "billing", events: { transport: rabbitmqEventTransport(connection, { service: "billing" }) } })` from the new entry point `@browserlessapi/inferlo/rabbitmq`, with a connection from amqplib's `connect()`. Events go to the durable topic exchange `inferlo.events` (routing key = event name) as persistent messages, and publishing waits for RabbitMQ's publisher confirm. Each service reads each event it subscribes to from its own durable queue `inferlo.<service>.<event name>` (a quorum queue, or `queueType: "classic"`), declared and bound at its first read, so every subscribed service gets each event once and its instances share the work. Delivery is at least once: an event is acknowledged after its jobs are queued, one whose jobs could not be queued is returned to its queue after `staleAfterMs`, and the events of an instance that stopped are returned when its connection closes. Trace context and tenant travel with the event; invalid arguments raise the new IL6054. amqplib is not a dependency and is never imported by Inferlo; tested against RabbitMQ 4.3 with amqplib 0.10.9 and the latest RabbitMQ and amqplib, on Node.js, Bun and Deno. Docs in jobs.md, errors.md and support.md, and the rabbitmq-events benchmark task.

- Pino: `createApp({ logger: pinoLogger(log) })` with `pinoLogger` from the new entry point `@browserlessapi/inferlo/pino` writes Inferlo's request, error, job and readiness logs through an app's pino logger (Fastify's `fastify.log`, the instance given to `nestjs-pino`, or `pino()`). Each entry is `log.info(fields, message)` or `log.error(fields, message)`: `requestId`, `traceId`, `spanId`, `method`, `path`, `status` and `durationMs` are top-level properties, errors are `err` for pino's error serializer, and other data is under `data`. Inferlo's secret redaction runs first, and pino's own `level`, `base`, `redact` and transports still apply. A pino logger passed to `createApp({ logger })` without `pinoLogger` now raises IL6053 instead of losing the request id and the error, and `pinoLogger` of anything that is not a logger raises IL6052. pino is not a dependency; tested on pino 9.14.0 and the latest release. New projects' AGENTS.md mention it; docs in observability.md, integrations.md, errors.md and support.md, and the pino-logger benchmark task.

- Events between services over NATS JetStream: `createApp({ name: "billing", events: { transport: natsEventTransport(nc, { service: "billing" }) } })` from the new entry point `@browserlessapi/inferlo/nats`. Events go to the shared stream `INFERLO_EVENTS` (created on first use, subjects `inferlo.events.<name>`, `Nats-Msg-Id` set to the event id for JetStream's duplicate window); each service reads each subscribed event through its own durable pull consumer, so every service gets each event once and its instances share the work. Delivery is at least once: an event is acknowledged after its jobs are queued, and one that fails or was never acknowledged is delivered again after `staleAfterMs`. Trace context and tenant travel with the event. `@nats-io/jetstream` (3.0.0 and later) is an optional peer dependency that the core package never imports; invalid arguments raise the new IL6051. Tested against a real nats-server on Node.js, Bun and Deno, with a new CI job on nats-server 2.11 with the first 3.x clients and the latest server and clients. Docs in jobs.md, errors.md and support.md, and the nats-events benchmark task.

- Zod, Valibot and ArkType schemas in the AI module: `ai.generate({ output })` and `tool(name, { input })` take any [Standard Schema](https://standardschema.dev) that implements Standard JSON Schema, next to Inferlo's `t.*` schemas, in `@browserlessapi/inferlo/ai` (any framework) and `ctx.ai`: `z.object()` (zod 4.2+), `type()` (arktype 2.1.28+) and `toStandardJsonSchema(v.object())` (`@valibot/to-json-schema` 1.5+). The model is shown the library's JSON Schema, the answer is validated by the library (transforms and defaults apply, mismatches go back to the model with the library's messages) and `object` and the tool's `input` have the library's output type. Anything else raises the new IL5032 before a model is called; tool inputs that are not object schemas raise IL5013. New export type `StandardSchema`; `ToolDef["input"]` is now `ObjectSchema | StandardSchema`. No runtime dependency: the libraries are only dev dependencies of the repository. A new CI job tests the first releases with Standard JSON Schema and the latest ones. Docs in ai.md, errors.md and support.md, and the ai-zod-output benchmark task.

- S3-compatible file storage: `createApp({ storage: s3Storage({ bucket, region, accessKeyId, secretAccessKey }) })` keeps files in AWS S3, Cloudflare R2 (`endpoint`, `region: "auto"`), MinIO or any store that speaks the S3 API, with `sessionToken` for temporary credentials, path-style or virtual-hosted addressing and a per-request `timeoutMs`. Requests are signed with AWS Signature Version 4 on Web Crypto and sent with `fetch`: no AWS SDK and no runtime dependency, wherever `fetch` and Web Crypto run. The signing is tested against AWS's published examples and AWS's own signer, and the store against a local S3 stand-in that checks every signature, payload hash and expiry. New `storage.url(key, { expiresIn })` returns a signed download URL (GET of that key only, `expiresIn` required, at most seven days); stores without signed URLs throw IL6050, and a `StorageStore` can add `url(key, expiresIn)`. Store errors are 502 IL6049 with S3's error code and never a credential; invalid options fail at startup with IL6048. New exports `s3Storage`, `S3StorageOptions` and `StorageUrlOptions`. Docs in storage.md and errors.md, the app template's AGENTS.md and the s3-signed-url benchmark task.

## 0.8.0 - 2026-11-07

- postgres.js: `postgres({ pool: postgresJsPool(sql) })` from the new entry point `@browserlessapi/inferlo/postgres-js` runs Inferlo's Postgres adapter on an app's postgres.js (`postgres` package) instance, so the app keeps one connection pool. Inferlo models, `db.$sql`, the database job queue, rate limits and the audit log run on postgres.js's connections, and inside `db.$transaction` the new `tx.$pgClient<PostgresJsClient<ReservedSql>>()` gives the transaction's reserved connection as `sql`, so postgres.js queries and Inferlo models commit or roll back together. postgres.js errors are read as `pg`'s (a unique violation is 409 IL4004). Anything but a postgres.js `sql` instance raises the new IL4029. New types `PostgresJsPool`, `PostgresJsClient`, `PostgresJsSql` and `PostgresJsQueryable`; `postgres` (3.4.0 and later) is a new optional peer dependency that the core package never imports. JSON fields and the job queue's `input` are now sent as text and cast to `jsonb` on the server, so drivers that encode parameters by the column's type do not store JSON text as a JSON string; `in` and `notIn` on JSON fields, which failed on Postgres with "malformed array literal", now compare each value as JSON. A new postgres.js section in docs/integrations.md, notes in database.md and errors.md, the support tables, the app template's AGENTS.md, the new `examples/with-postgres-js`, the model, relation, pagination, job queue, rate limit and audit log tests running on both drivers (Node.js, Bun and Deno), a new CI job on postgres.js 3 (newest 3.x) with PostgreSQL 14 and the latest postgres.js with the latest PostgreSQL, and the postgres-js-pool benchmark task.

- Single sign-on with OpenID Connect (part 2): `routes: [sso]` adds `POST /auth/logout` (`sso.logoutPath`, new `sso.oidcLogout` route), which ends the app's session and sends the browser to the provider's `end_session_endpoint` (OpenID Connect RP-Initiated Logout) with the ID token as `id_token_hint`, the `client_id` and `post_logout_redirect_uri` (the new `postLogoutRedirectUri` option, by default the app's origin). A signed-in browser must send the session's CSRF token (403 IL3005 without it). The ID token is kept for this in an `HttpOnly`, `SameSite=Lax` cookie (`inferlo_oidc_id`, `__Host-` on https) and is only sent back to the provider that issued it; providers without an `end_session_endpoint`, or that cannot be reached, still end the app's session. The new `authorizationParams` option adds parameters to every sign-in (`prompt`, Google's `hd`, Entra ID's `domain_hint`), refusing the flow's own (IL6047), and the login link takes `?loginHint=` and `?prompt=`. Docs in auth.md and errors.md, the app template's AGENTS.md, tests against the local stand-in provider and oidc-provider (sign-out confirmed at the provider and back at the registered URI), and the oidc-logout benchmark task.

- MikroORM: an app that uses MikroORM 6 or 7 on Postgres (often with NestJS) can add Inferlo next to it. A new MikroORM section in docs/integrations.md covers MikroORM's pool and Inferlo's `postgres({ pool })` on one database, a forked EntityManager per request in routes and jobs, Inferlo models next to MikroORM's entities, a write across a MikroORM table and an Inferlo model in one `db.$transaction` with MikroORM's table written through `tx.$sql`, and the shutdown order. MikroORM's schema generator (`schema:update`, `migration:create`) plans to drop every table that is not one of its entities, Inferlo's included, so the guide and the example set `schemaGenerator: { skipTables: [...models.map((m) => m.name), /^inferlo_/, "audit_log"] }`. The new `examples/with-mikro-orm` (entities with `defineEntity`, no decorators) tests the transaction and its rollback on a foreign key and a unique error, the pool after failed transactions, relations read through MikroORM, 404s, and both migration directions, including the drop MikroORM plans without `skipTables`. A new CI job runs it with MikroORM 6 (newest 6.x) on PostgreSQL 14 and the latest MikroORM on the latest PostgreSQL; the main and Deno jobs run it too. MikroORM is a dev dependency of the repository only; the core package is unchanged. The support tables, the app template's AGENTS.md and the mikro-orm-skip-tables benchmark task are updated.

- Single sign-on with OpenID Connect (part 1): `oidc({ issuer, clientId, clientSecret, session, userId })` signs browser users in with Okta, Microsoft Entra ID, Google Workspace, Auth0, Keycloak or any OpenID Connect provider and ends in a `sessions()` cookie. `routes: [sso]` adds `GET /auth/login` (`?returnTo=/path`, kept on the app) and `GET /auth/callback`. The authorization code flow uses PKCE (S256), a one-time state and nonce in a short-lived `HttpOnly` cookie (`__Host-` on https), checks the `iss` response parameter (RFC 9207), exchanges the code with `client_secret_basic` (or `client_secret_post`, or as a public client), and verifies the ID token's signature against the provider's keys, its issuer, audience (and `azp`), expiry and nonce with Web Crypto. `userId(claims, { db, req, tokens })` picks the app's user or refuses the sign-in (403 IL3011). Failed checks answer 400 IL3009; an unreachable provider or a wrong client secret 502 IL3010. New export `oidc` and the types `Oidc`, `OidcOptions`, `OidcClaims` and `OidcTokens`, new codes IL3009, IL3010, IL3011 and IL6047, no runtime dependencies. `jwt()`'s token checks moved into a shared internal verifier. Docs in auth.md ("Single sign-on with OpenID Connect"), security.md and errors.md, the support tables and the app template's AGENTS.md; tests against a local stand-in provider and against oidc-provider (a certified OpenID Connect server) on Node.js, Bun and Deno, with a new CI job on oidc-provider 9.0.0 and latest; and the oidc-login benchmark task.

- Passport.js: `passportSession({ user, trustedOrigins, roles, tenant })` from the new entry point `@browserlessapi/inferlo/passport` makes the user Passport puts on `req.user` the auth of an Inferlo app mounted in Express (or node:http) with `toNodeHandler` after `passport.session()`, so Express apps with Passport strategies adopt Inferlo without a second sign-in. Routes get `{ id, email, name, roles }` from Passport's user (a numeric id becomes a string, `name` from `name` or `displayName`) or what `user(passportUser, { db, req, nodeRequest })` returns. Logins from the `express-session` cookie are refused with 403 IL3007 for cross-site changes, as for Better Auth and Auth.js; strategies with `session: false` work too and are not checked. An app not given a Node.js request, or a Passport user without an id, answers 500 IL6046 with the fix in the log. New codes IL6045 and IL6046. Web Requests built by `toNodeHandler`, `fromNodeRequest` and the h3 and WebSocket bridges now remember the Node.js request they came from (internally). Docs in auth.md, integrations.md and errors.md, the support tables, the app template's AGENTS.md, tests on Node.js and Bun, a new CI job on `passport` 0.6.0 and the latest Passport (and the Express jobs on Express 4 and 5), and the passport-session benchmark task. - New entry point `@browserlessapi/inferlo/ai`: the AI module on its own, for use in any framework or script without `createApp`. `import { createAI, anthropic, t } from "@browserlessapi/inferlo/ai"` gives aliases with fallback, structured output, streaming, embeddings, image input and usage tracking, and never loads the router, database or jobs code. It exports `createAI`, `cosineSimilarity`, `extractJson`, every provider, `mockProvider`, `ProviderError`, `t`, `Schema`, `ObjectSchema`, `ArraySchema`, `ValidationError`, `toJSONSchema`, `InferloError`, `env` and the AI types. See docs/ai.md, "Use it without createApp".
- Fix: `--json` CLI errors now always include `fix` and the real `message` in `error`, also for errors with a 500 status such as IL8007 and IL8008 from `inferlo worker`. Before, they went through `InferloError.toJSON()`, which hides both from API clients for server errors.

## 0.4.0 - 2026-11-04

- Cron: `export const nightly = cron("0 3 * * *", cleanupJob)` next to the job in a jobs module queues the job on a schedule while `app.jobs.start()` or `inferlo worker` runs. Five fields in UTC (numbers, `*`, ranges, lists, steps, month and weekday names). Each tick is queued once with a fixed job id, so with the database queue every instance can run the schedule; after a pause only the latest missed tick is queued. Registering a cron registers its job. The job runs with input `{}`. New code IL6013 (invalid schedule or job); new exports `cron`, `isCron` and type `CronDef`; `app.jobs.crons` and `describe().crons` list the schedules, and `inferlo describe` shows them.
- Background jobs, part 3: `inferlo worker` runs the app's jobs in their own process. It reads `.env` like `inferlo dev`, calls `app.jobs.start()`, and on SIGTERM or Ctrl+C waits for the running job, closes the database and exits 0 (a second signal exits at once); `--json` prints `started` and `stopped` events. It needs registered jobs (new code IL8007) and the database job queue (new code IL8008). New projects run jobs in `src/server.ts` with `app.jobs.start()`, stop them on SIGTERM, and have a `worker` script. `app.jobs.queue` and `describe().jobQueue` say where jobs are kept.
- Background jobs, part 2: `createApp({ jobQueue: { store: "database" } })` keeps queued jobs in the Postgres table `inferlo_jobs` (created on first use), so they survive restarts and are shared by every instance. Due jobs are claimed with `FOR UPDATE SKIP LOCKED`, so each attempt runs on one instance only, and an instance only claims jobs it has registered. A running job's worker reports every 30 seconds; a job left `"running"` for 5 minutes without a report (its process stopped) is run again as its next attempt, or marked `"failed"` when it has no attempts left. The default store stays `"memory"`. New codes IL6011 (invalid `jobQueue`) and IL6012 (database store without Postgres); new type `JobQueueConfig`.
- Background jobs, part 1: `job("send-email", { input: schema, retries: 3 }).handle(async ({ input, db, ai, jobs, attempt }) => ...)` defines a job, `createApp({ jobs: [jobs] })` registers jobs (or modules of them), and `ctx.jobs.enqueue(sendEmail, { to })` in a route handler (or `app.jobs.enqueue` anywhere) queues one with typed input, validated when queued (IL1001) and again when it runs, stored as JSON, with an optional `runAt`. Failed attempts are retried after 10s, 20s, 40s and so on (at most an hour) until the retries are used up, then the job is marked `"failed"` and logged. `app.jobs.start()` runs due jobs in the process and `stop()` waits for the running one; `app.jobs.runDue()` runs every due job once for tests, and `app.jobs.get(id)` returns a job's record. The queue is kept in memory for now; a Postgres-backed queue and `inferlo worker` come next. New codes IL6009 (invalid job) and IL6010 (job not registered); `describe()` and `inferlo describe` list jobs; route handlers get `jobs` in their context. New docs page docs/jobs.md.
- Vision input: `ai.generate({ prompt, images: [{ url: "https://..." }] })` or `images: [{ base64, mediaType: "image/png" }]` sends images to the model with the prompt, and user messages take `images` too (`messages: [{ role: "user", content, images }]`). Works with Anthropic (image blocks, `data:` URLs sent as base64), OpenAI, Gemini, Ollama and OpenAI-compatible providers (`image_url` parts), with `ai.stream`, structured output and tools. Remote URLs go to the provider unchanged; Inferlo never downloads them. Invalid images (other URL schemes, unsupported media types, invalid base64, images on non-user messages, `images` without `prompt`) raise the new code IL5012 before any model is called. New types `Image` and `ImageMediaType`; `Message` has an optional `images` field.
- Reverse (has-many) relations: `db.users.findMany({ include: { tickets: true } })` adds `user.tickets`, every row of a model whose `t.ref` field named `<name>Id` points to that user (`[]` when there are none), with one extra query per relation for all rows, ordered by `createdAt`. The relation is named after the other model's table; when that table has several ref fields to this model, each is named `<table>By<Name>` (`ticketsByOwner`, `ticketsByAssignee`) and the plain table name raises IL4023 as ambiguous. Works on `findMany`, `findOne`, `find` and `get`, together with forward relations, and is typed (`Row<typeof Ticket>[]`). New type `ReverseRelations`; `Include` takes the app's models as an optional second type parameter.
- Rate limiting: `route.post(path, { rateLimit: { max: 10, per: "minute", by: "user" | "ip" } })` answers 429 with the new code IL2005 and a `Retry-After` header once the limit is passed, and sends `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` headers. Counts are per route, per signed-in user (the default; requests without a user count by IP) or per IP, in fixed windows, kept in memory or with `createApp({ rateLimit: { store: "database" } })` in the Postgres table `inferlo_rate_limits`, shared by every instance. New `createApp({ trustProxy: true })` uses the first `X-Forwarded-For` address as the client IP behind a proxy. Invalid options raise IL6007 and the database store without Postgres raises IL6008. `describe()` and OpenAPI show the limit. The new app template limits the AI summary route to 20 calls per hour per user.
- Relations: `db.tickets.findMany({ include: { owner: true } })` loads the row each `t.ref` field points to, for every field named `<name>Id` (`ownerId` gives `owner`), with one extra query per relation for all rows (no N+1). Results are typed (`tickets[0].owner` is `Row<typeof User>`, or `| null` for optional and nullable refs). `find`, `get` and `findOne` take `{ include }` as a new optional second argument. Unknown relation names raise the new code IL4023. `t.ref()` now returns a `RefSchema` that keeps the table name in its type; new types `Include`, `Relations`, `WithInclude`, `FindOptions`.
- Tool calling: `ctx.ai.generate({ prompt, tools: [createTicket, getTicket], maxSteps: 5 })` lets the model call your routes as tools. Each call runs as an HTTP request to the route as the current user, so auth, roles and validation apply; errors (403, 404, 422) go back to the model so it can correct itself. Works with Anthropic, OpenAI, Gemini and OpenAI-compatible providers. The result has a new `steps` list with every model call, its tool calls (`name`, `input`, `status`, `output`, `isError`) and usage; `usage` has the totals. `allow` is checked again before each model call that follows tool calls, and once a tool has run Inferlo does not fall back to another model (IL5006). New codes: IL5009 (tools outside a route handler), IL5010 (step limit reached), IL5011 (tool is not a registered route). `Message` has optional `toolCalls`, `toolCallId` and `isError` fields and a `"tool"` role, `ProviderRequest` has `tools`, and `mockProvider` can return `{ toolCalls }`. New types: `ToolCall`, `ToolSpec`, `ToolCallResult`, `Step`, `MockReply`.
- `inferlo db migrate --allow-change` now also generates column type changes, for example `t.string().max(120)` to `.max(200)`, `t.text()` to `t.int()` or `t.int()` to `t.number()`: `ALTER TABLE "posts" ALTER COLUMN "title" TYPE varchar(200)`, with a strict `USING` clause when Postgres needs one (other types go through their text, jsonb through its JSON text, and a field becoming `t.json()` through `to_jsonb`). A fixed default is dropped before the change and set again after it. Without the flag these changes are refused with IL4019 (they were IL4013). Values are never cut, rounded or set to NULL: if `--apply` finds one that does not convert, it fails with the new code IL4022, naming the columns and the value, and nothing from that migration is kept. IL4013 now only covers renames, reference and index changes.
- `inferlo db migrate --allow-change` now also generates enum value changes: adding or removing values of a `t.enum` field, or turning a text field into an enum or back, replaces the column's CHECK constraint (`ALTER TABLE ... DROP CONSTRAINT "posts_kind_check"`, then `ADD CONSTRAINT "posts_kind_check" CHECK (...)`, with the name Postgres gave it). Without the flag these changes are refused with IL4019 (they were IL4013). If `--apply` finds rows that still use a removed value, it fails with the new code IL4021, naming the table and constraint, and nothing from that migration is kept.
- CI also tests Node.js 26, the newest LTS line.
- Docs: the framework and app AGENTS.md files now say error codes are `ILxxxx` (they still said `KRxxxx`).

## 0.3.0 - 2026-11-02

- **Breaking: Kairo is now Inferlo.** The npm package is `@browserlessapi/inferlo` (was `@browserlessapi/kairo`), the CLI is `inferlo` (was `kairo`), the GitHub repository is `BrowserlessAPI/Inferlo`, and error codes start with `IL` instead of `KR` (same numbers: KR1001 is now IL1001). `KairoError` is now `InferloError`, `KAIRO_VERSION` is `INFERLO_VERSION`, and `describe()` reports the version as `inferlo`. Environment variables for tests and the benchmark start with `INFERLO_`. To upgrade, replace the package name in imports and package.json, `kairo` with `inferlo` in scripts, and `KR` with `IL` where you match error codes.
- Existing projects keep working: `inferlo db migrate --apply` renames an existing `kairo_migrations` table to `inferlo_migrations` (history is kept), snapshots with the old `"kairo"` key are read, and the `"kairo"` section in package.json is still read for `entry` and `server`.

- Breaking: the minimum supported Bun version is now 1.3.0. Bun 1.2 releases skip or misorder `node:test` subtests, so Inferlo's test suite cannot verify them.

- CI tests every supported version at both ends: Node.js 22.18, 22, 24 and current; Bun 1.3.0 and latest; PostgreSQL 14 to 18 and latest; TypeScript 5.9 and latest. A weekly run catches new upstream releases.

- `inferlo db migrate --allow-change` generates default and required/optional changes of existing columns (`ALTER COLUMN ... SET DEFAULT`, `DROP DEFAULT`, `SET NOT NULL`, `DROP NOT NULL`). Making a column required with a fixed default first fills NULL rows with it. Without the flag these changes are refused with the new code IL4019 (they were IL4013) and nothing is written. If `--apply` hits NULL rows in a column made required, it fails with the new code IL4020, naming the table and column. Also available as `planMigration(models, snapshot, { allowChange: true })`; the plan now includes `changes`, and `--json` output has a `changes` list. IL4013 now covers type, enum value, reference and index changes.
- `migrations/snapshot.json` now describes each column as a structured object (`{ type, notNull, default?, enum?, references?, primaryKey? }`, format `"inferlo": 2`) instead of its SQL text. Snapshots written by 0.2.0 (`"inferlo": 1`) are read and upgraded automatically, and saved in the new format with the next generated migration. IL4013 now says what changed in each column (for example `change column posts.title (type varchar(120) -> varchar(200))`) and lists it in `details.columns`. Types: `MigrationSnapshot` is the new format; `MigrationSnapshotV1` (the old one) and `MigrationSnapshotColumn` are new exports, and `planMigration` accepts either format.
- `inferlo db migrate --apply` records a SHA-256 checksum of each migration file in `inferlo_migrations` and warns with the new code IL4018 when a file that was already applied has been edited since (it is not run again; pending files are still applied). `--json` output has a new `edited` list, and `applyMigrations(db, migrations, { onEdited })` reports the names. Line ending changes do not count as edits. Existing `inferlo_migrations` tables get a `checksum` column automatically, filled from the current files on the next run.
- `inferlo db migrate --allow-drop` generates drops of removed tables, columns and indexes (`DROP TABLE`, `ALTER TABLE ... DROP COLUMN`, `DROP INDEX`, never `CASCADE`), with a warning comment in the file. Without the flag, drops are refused with the new code IL4017 and nothing is written. Also available as `planMigration(models, snapshot, { allowDrop: true })`; the plan now includes `drops`, and `--json` output has a `drops` list. IL4013 now only covers column and index changes.
- Docs: Inferlo is now described as "the TypeScript backend framework with built-in AI model support", with a new "AI models built in" section in the README.
