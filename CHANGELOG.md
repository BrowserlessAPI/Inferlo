# Changelog

All notable changes are listed here. Inferlo follows [semantic versioning](https://semver.org); until 1.0, minor versions may include breaking changes, always listed under "Breaking".

## Unreleased

- Audit log (permissions, part 2): add the built-in `AuditLog` model to `createApp({ models })` (the `audit_log` table, created by `inferlo db migrate`) and call `await audit("tickets.update", { model: "tickets", before: ticket, after: updated })` in a route or job. Each entry records the action, the signed-in user (jobs pass `userId`, or none for system work), the model and record id (defaulting to `after.id` or `before.id`), the changed fields as `{ field: { from, to } }` (creates and deletes too; `id`, `createdAt` and `updatedAt` skipped, dates as ISO strings), optional `data`, the source (`"PATCH /tickets/:id"` or `"job export-tickets"`) and the request id. Changed fields named like passwords, tokens, secrets, API keys, hashes, sessions or cookies are stored as `"[redacted]"`, the same names in `data` are redacted, and `createApp({ redact })` values and AI provider keys are replaced in any string. New `ctx.audit` in routes and jobs, new exports `AuditLog` and `auditChanges`, new types `Audit`, `AuditEntry` and `AuditChange`, and new code IL6027 (no `AuditLog` model, an empty action or an invalid entry). Docs in docs/auth.md, "Audit log", a rule in the app AGENTS.md and the audit-log benchmark task.

- Next.js: new entry point `@browserlessapi/inferlo/nextjs`. In an App Router catch-all route, `export const { GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS } = toNextHandlers(app, { prefix: "/api" })` (in `app/api/[[...path]]/route.ts`) serves a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) with the prefix removed from the path; requests outside it keep their path, and request bodies and AI streams pass through unchanged. `@browserlessapi/inferlo/ai` works in server actions and server components. No runtime dependency on Next.js. New code IL5020 (not an app, or a prefix that does not start with `/`), new types `NextHandlers`, `NextHandlersOptions` and `NextRouteHandler`, a Next.js section in docs/integrations.md, example examples/with-nextjs (route handlers and a server action) and the nextjs-route-handlers benchmark task. CI tests Next.js 15 (newest 15.x, still maintained upstream) and the latest Next.js with Next.js's own `NextRequest`.

- Permissions (part 3): add `permissions: typeof access` to `Register` and the route option `permission` only accepts the names of rules that need nothing but `{ user }` (roles rules and functions of the user alone), so a misspelled name, or a rule that also needs a record, is a type error. Without it, `permission` still takes any string and `createApp` checks it at startup. New exported type `AppPermission`. MCP `tools/list` now leaves out tools whose role (`auth: "admin"`) or `permission` the caller does not have, so AI agents only see tools they may call; tools that only need sign-in stay listed for anonymous callers, `tools/call` checks every call as before, and a rule that throws while listing hides its tool. The helpdesk example registers its permissions, docs in docs/auth.md, "Typed permission names", and the typed-permissions benchmark task.

- Koa: new entry point `@browserlessapi/inferlo/koa`. `koa.use(inferloAI(ai))` puts an AI client (`createAI(...)` or an Inferlo app's `app.ai`) on every context as `ctx.ai`, typed through Koa's `DefaultContext`. `koa.use(toKoaMiddleware(app, { prefix: "/api" }))` runs a whole Inferlo app (routes, auth, validation, OpenAPI and MCP) under a path and passes other requests to the next middleware; with `fallthrough: true` it answers only the app's routes, so routes move from Koa one at a time at the same URLs. A body a Koa body parser already read (`ctx.request.body`) is used. `sendResponse(ctx, response)` streams a Web Response, such as an AI stream. No runtime dependency on Koa. IL5014 now also covers the Koa middleware, and invalid `toKoaMiddleware` options raise IL5019. New types `KoaContextLike` and `KoaMiddleware`, example examples/with-koa and the koa-mount benchmark task. CI tests Koa 2 (newest 2.x) and the latest Koa.

- Permissions (part 1): `permissions({ "reports.view": { roles: ["admin", "analyst"] }, "tickets.update": ({ user, ticket }) => ticket.ownerId === user.id })` defines named permissions once. `await access.can(name, { user, ticket })` returns true or false and `await access.authorize(name, { user, ticket })` throws IL3004 (403), or IL3001 (401) without a user, the same in routes, AI tools and jobs; the input is typed from the rule. Deny by default: no user, an unknown name or a rule that does not return true or false never allows. With `createApp({ permissions: access })`, the route option `permission: "reports.view"` is checked with `{ user }` before the handler, also when a model calls the route as a tool; `createApp` checks every route's permission at startup. `describe()` has `permissions` and each route's `permission`, `inferlo describe` shows them, and OpenAPI adds `x-inferlo-permission` and a 403 response. New codes IL3004 (permission denied) and IL6026 (invalid permissions), new exports `permissions`, `isPermissions` and the types `Permissions`, `PermissionRule` and `PermissionInput`. Docs in docs/auth.md, "Permissions", a rule in the app AGENTS.md and the note-permissions benchmark task.

- Encore.ts: an Encore raw endpoint serves a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) with `api.raw({ expose: true, method: "*", path: "/inferlo/*rest" }, toNodeHandler(app, { prefix: "/inferlo" }))`, or every path Encore has no endpoint for with Encore's fallback path `/!rest`, and `createAI` from `@browserlessapi/inferlo/ai` works in Encore services with the API key from an Encore secret. No new entry point and no dependency on Encore. New example examples/with-encore, whose tests run its endpoints with the real encore.dev package and Encore's own raw request and response classes, an Encore.ts section in docs/integrations.md and the encore-raw-endpoint benchmark task. CI tests encore.dev 1.51.0 and the latest encore.dev.

- Fix: `toNodeHandler` and `fromNodeRequest` only use `req.body` instead of the request stream when it holds a body a parser already read (a string, bytes, or a plain object or array). Before, any `req.body` was used, so a request whose `body` field is the host's own object, such as the body reader of an Encore raw request, reached the app as `{}` and failed validation.

- Docs: new guide docs/migrate-from-hono.md. It moves a Hono app to Inferlo one route at a time on the same runtime, with every URL unchanged: Hono's routes come first and `hono.all("*", (c) => inferlo.fetch(c.req.raw))` passes everything else to Inferlo. It ports a route with its Zod validator and auth middleware, maps Hono concepts and middleware (validators, `HTTPException`, bearer and JWT auth, cors, secure-headers, logger, request-id, timeout, sub-apps, `basePath`, zod-openapi, RPC, streaming, bindings) to Inferlo, shares one auth check between both, and ends with removing Hono. A new test checks the recommended setup on Hono 4.0.0 and the latest Hono.

- API versions (API versioning, part 2): `apiVersion("v1", [ticketsV1, account], { deprecated: { since, sunset, link } })` serves routes under `/v1` as API version v1. A route that did not change can be in several versions; each gets its own copy under its prefix, named `<version>_<export name>` (`v1_listTickets`) so operation ids and MCP tool names stay unique. `deprecated` on a version marks all its routes (a route's own option wins). Each version has its own OpenAPI document at `/<version>/openapi.json` (its routes and the routes outside every version), also as `app.openapi({ version: "v1" })`. `describe()` has `versions` and each route's `version`, and `inferlo describe` shows them. New code IL6025 (invalid version, a route in two versions, unknown version, a route on a version's document path), new type `ApiVersionOptions`, and the api-versions benchmark task.

- Docs: new guide docs/migrate-from-nestjs.md. It moves a NestJS app to Inferlo one route at a time while both run in one process and every URL stays the same, maps NestJS concepts (modules, controllers, providers and injection, DTOs and pipes, guards, interceptors, exception filters, Swagger, config, throttler, terminus, schedule, testing modules) to Inferlo, turns Nest feature modules into Inferlo modules with services as plain functions in `provides`, shares one auth check between guards and Inferlo, and ends with removing NestJS. A new test checks the recommended setup on NestJS 11.0.0 and the latest NestJS.

- `toNodeHandler(app, { fallthrough: true })`: the app answers only requests it has a route for (method and path) and its own endpoints (OpenAPI, MCP, health, metrics and CORS preflights of its paths), and passes everything else to the host framework's `next()`. Mounted before the host's routes (`nest.use(toNodeHandler(inferlo, { fallthrough: true }))`), routes move to Inferlo one at a time at the same URLs, even when the host keeps other methods on the same path. New code IL5019 (invalid option, or `fallthrough` with something that is not an app from `createApp`) and the node-fallthrough benchmark task.

- Modules: `module("billing", { description, imports: [users], models, routes, jobs, provides })` groups one feature's models, routes and jobs, and `createApp({ modules: [users, billing] })` adds them to the app. Modules are plain frozen values: no decorators, no container, no injection; other modules call what a module `provides` directly (`users.provides.getUser(db, id)`). `createApp` checks that every imported module is registered, that names are unique, that a model belongs to one place, and that models only reference (`t.ref`) models of their own module, an imported module or the app. `app.modules` lists the modules and `app.db` is typed from their models (`ModuleModels<...>`). `describe()` has a `modules` list (imports, models, routes, jobs and provides of each) and marks models, routes and jobs with their `module`; `inferlo describe` prints a Modules section; OpenAPI tags module routes with the module name and lists the modules as tags. New codes IL6022 (invalid module), IL6023 (modules do not fit together) and IL6024 (reference to a module that is not imported), new types `Module`, `ModuleOptions`, `AnyModule` and `ModuleModels`. New docs page docs/modules.md and the feature-module benchmark task.

## 0.5.0 - 2026-11-04

- Docs: new guide docs/migrate-from-express.md. It moves an Express app to Inferlo one route at a time while both run in one process and every URL stays the same (the Inferlo app mounted with `toNodeHandler(app)` after the Express routes), maps Express concepts and packages (validators, Passport, cors, helmet, express-rate-limit, morgan, dotenv, swagger-jsdoc, supertest) to Inferlo, shares one auth check between both, and ends with removing Express. A new test checks the recommended setup on Express 4 and 5.

- Deprecated routes (API versioning, part 1): `route.get("/v1/tickets", { deprecated: { since: "2026-11-01", sunset: "2027-06-30", link: "https://example.com/docs/tickets-v2" } })` sends `Deprecation: @<since>` (RFC 9745), `Sunset` (RFC 8594) and `Link: <...>; rel="deprecation"` on every response of the route, errors included. `deprecated: true` only marks the route. OpenAPI marks the operation `deprecated` (dates and link in `x-inferlo-deprecation`), `describe()` and `inferlo describe` show it, and MCP tool descriptions say the tool is deprecated so AI agents prefer others. New code IL6021 (invalid option), new type `Deprecation`, and the deprecate-route benchmark task.

- Ts.ED: new entry point `@browserlessapi/inferlo/tsed` with `InferloAI` and `inferloAI(ai)`. `@Configuration({ imports: [inferloAI(ai)] })` (or the same in `PlatformExpress.bootstrap` settings and `PlatformTest.create`) registers an AI client (`createAI(...)` or an Inferlo app's `app.ai`) for injection, and `InferloAI` is both the token and the type: `constructor(private readonly ai: InferloAI)`, `@Inject(InferloAI)` or `inject(InferloAI)`. A factory with the same token creates the client at startup. A whole Inferlo app mounts on the Express platform with `toNodeHandler` in `$beforeRoutesInit`. No runtime dependency on Ts.ED. IL5014 now also covers `inferloAI()` from this entry point. New example examples/with-tsed and the tsed-ai-service benchmark task. CI tests Ts.ED 8.0.1 and the latest Ts.ED.

- Observability, part 2: Prometheus metrics. `createApp({ metrics: { token: settings.METRICS_TOKEN } })` serves `GET /metrics` in the Prometheus text format: `inferlo_http_requests_total` (by method, route pattern and status), `inferlo_http_request_duration_seconds` (histogram by method and route), `inferlo_http_requests_in_flight`, `inferlo_job_runs_total` and `inferlo_job_duration_seconds` (by job and outcome), `inferlo_ai_calls_total`, `inferlo_ai_tokens_total`, `inferlo_ai_cost_usd_total` and `inferlo_ai_call_duration_seconds` (by requested alias and the model that answered), and `inferlo_info`. Routes are labelled by pattern (`/tickets/:id`), unknown methods count as `OTHER`, and health and metrics requests are not counted, so the number of series stays small. With `token`, scrapers must send `Authorization: Bearer <token>` (compared in constant time; `{ token: undefined }` is refused rather than made public); `path` and histogram `buckets` can be changed. New code IL6020 (invalid metrics options), new type `MetricsConfig`, `describe().endpoints.metrics`, and `inferlo describe` shows the endpoint. New projects serve metrics when `METRICS_TOKEN` is set. New benchmark task prometheus-metrics.

- AdonisJS: new entry point `@browserlessapi/inferlo/adonisjs`, an AdonisJS provider. Add `() => import("@browserlessapi/inferlo/adonisjs")` to the providers in `adonisrc.ts` and export the AI client from `config/ai.ts` (`export default createAI({ providers, models })`): the provider binds it in the container as `ai` (`await app.container.make("ai")`) and adds `ctx.ai` to every HTTP context, both typed. The client is checked when the app boots. It never loads the router, database or jobs code, and loads nothing from AdonisJS until the provider boots. IL5014 now also covers the provider; new code IL5018 (no `config/ai.ts`); new type `AdonisApplicationLike`. New example examples/with-adonisjs and the adonisjs-provider benchmark task. CI tests AdonisJS 6.2.0 and the latest AdonisJS (7, on Node.js 24).

- Docs: new support policy, docs/support.md. It defines Inferlo's public API (exports, error codes, CLI and `--json` output, HTTP behaviour, migration files and tables), semantic versioning before and after 1.0, which versions get bug and security fixes (from 1.0: the latest minor, plus security fixes for the previous major for 12 months after a new major), the deprecation process (marked `@deprecated`, a migration note, removal no earlier than the next major), and every supported runtime, database and framework version with how end of life is handled.

- Observability, part 1: request ids, request logs and JSON logs. Every response now has an `X-Request-Id` header (a random UUID, or with `trustProxy: true` a safe id sent by the proxy), handlers and middleware get it as `ctx.requestId`, and every log entry for a request (failed requests, `ctx.waitUntil` errors) carries it. `createApp({ logging: { requests: true } })` logs each request's method, path, status and duration (health endpoints are skipped), and `logging: { format: "json" }` makes the built-in logger write one JSON object per line (`time`, `level`, `app`, `msg`, fields such as `requestId`, and errors as `{ name, message, code, status, stack, cause }`), redacted like every log entry. Custom loggers get the fields as a new optional third argument: `info(message, data, fields)`. New code IL6019 (invalid `logging`), new types `LoggingConfig` and `LogFields`, `describe().logging`, and `inferlo describe` shows it. New projects log every request. New docs page docs/observability.md and the request-logging benchmark task.

- tRPC: new entry point `@browserlessapi/inferlo/trpc`. `trpc.procedure.use(inferloAI(ai))` is a tRPC middleware that adds an AI client (`createAI(...)` or an Inferlo app's `app.ai`) to the context as `ctx.ai`, typed next to the app's own context. Inferlo schemas (`t.object(...)`) work as tRPC inputs with typed `input`, and `ai.stream(...)` can be `yield*`ed from subscriptions and streamed queries. `trpcTools(router, { caller: router.createCaller(ctx), procedures: { "tickets.create": "Create a ticket." } })` turns queries and mutations into tools for `ai.generate({ tools })`, named after their path (`tickets_create`), with the procedure's `t.object` input, run through the caller so the procedure's middleware and auth apply; 4xx TRPCErrors go back to the model as failed tool results. It has no runtime dependency on tRPC and never loads the router, database or jobs code. IL5014 now also covers the tRPC middleware; new code IL5017 (invalid `trpcTools()` options); new types `TrpcToolsOptions` and `TrpcToolProcedure`. New example examples/with-trpc and the trpc-ai-tools benchmark task. CI tests tRPC 11.0.0 (tRPC 10 is no longer maintained) and the latest tRPC.

- NestJS: new entry point `@browserlessapi/inferlo/nestjs` with `InferloModule` and the injection token `INFERLO_AI`. `imports: [InferloModule.forRoot({ ai })]` provides an AI client (`createAI(...)` or an Inferlo app's `app.ai`) to every module (global by default, `global: false` to opt out), injected with `@Inject(INFERLO_AI) private readonly ai: AI`; `InferloModule.forRootAsync({ imports, inject, useFactory })` creates it from other providers such as `ConfigService` when Nest starts. A whole Inferlo app mounts with `nest.use("/api", toNodeHandler(inferlo))`. It has no runtime dependency on NestJS and never loads the router, database or jobs code. IL5014 now also covers `InferloModule`; new code IL5016 (missing options); new types `InferloModuleOptions` and `InferloModuleAsyncOptions`. New example examples/with-nestjs and the nestjs-ai-module benchmark task. CI tests NestJS 11.0.0 (the oldest major with security support) and the latest NestJS.

- Secret redaction: everything an app logs (failed requests, failed jobs, readiness checks, shutdown) and the messages `exposeErrors` shows now have credentials replaced with `"[redacted]"`: `Authorization`, `Cookie`, `Set-Cookie` and `X-Api-Key` header values (also inside error text and JSON), `Bearer` and `Basic` credentials, passwords in URLs and connection strings, secrets in query strings, common API key formats, and the API keys of the app's AI providers, even when a provider echoes one in an error. In logged objects, values under keys such as `password`, `token`, `secret` and `apiKey` are hidden. New option `createApp({ redact: [settings, "other value"] })` hides the `secrets` of a `config()` result and any other values. Logged errors keep their class, `code`, `status` and `cause`. The standalone `createAI` and `serve()` redact what they log too. New code IL6018 (invalid `redact`). New projects pass `redact: [settings]`. Docs in docs/security.md, "Secrets in logs", and the secret-redaction benchmark task.

- ElysiaJS: new entry point `@browserlessapi/inferlo/elysia` with `inferloAI(ai)`, an Elysia plugin that decorates the context with an AI client (`createAI(...)` or an Inferlo app's `app.ai`): `new Elysia().use(inferloAI(ai)).post("/classify", ({ ai }) => ...)`, typed in every handler. A whole Inferlo app mounts with `elysia.mount("/api", inferlo.fetch)` (routes, auth, validation, OpenAPI and MCP under the path). It has no runtime dependency on Elysia and never loads the router, database or jobs code. IL5014 now also covers the Elysia plugin. New example examples/with-elysia and the elysia-ai-plugin benchmark task. CI tests Elysia 1.0.0 and the latest Elysia, each on Node.js and Bun.

- Request timeouts: every route now has 60 seconds to read its body and run its handler, then answers `503` with the new code IL2007. Change the default with `createApp({ requestTimeoutMs: 30_000 })`, give a route its own limit with `route.post(path, { timeoutMs: 120_000 })`, or turn it off with `false`. Handlers get `ctx.signal`, an `AbortSignal` aborted on timeout or when the client disconnects; `ctx.ai` calls (`generate`, `stream`, `embed`) use it unless they pass their own `signal`, so model calls stop with the request, and after a timeout new `ctx.db` queries fail with IL2007 instead of running (client disconnects never cancel queries). New code IL6017 (invalid timeout); `describe()` has `requestTimeoutMs` and each route's own `timeoutMs`. **Breaking:** routes that take longer than 60 seconds now answer 503; give them a `timeoutMs`. Docs in docs/security.md, "Request timeouts", and the request-timeout benchmark task.

- Fastify: new entry point `@browserlessapi/inferlo/fastify` with `inferloPlugin`. `await fastify.register(inferloPlugin, { ai })` decorates `fastify.ai` and `request.ai` for the whole Fastify app (typed: importing the entry point adds `ai` to `FastifyInstance` and `FastifyRequest`), and `await fastify.register(inferloPlugin, { app, prefix: "/api" })` serves a whole Inferlo app under the prefix (routes, auth, validation, OpenAPI, MCP), with Inferlo reading the body itself so forms and `maxBodySize` work while Fastify's parsers stay as they are for other routes. Without `ai`, `fastify.ai` is the app's `app.ai`. It has no runtime dependency on Fastify and never loads the router, database or jobs code. IL5014 now also covers `inferloPlugin`; new code IL5015 (invalid plugin options); new types `InferloPlugin` and `InferloPluginOptions`. New example examples/with-fastify and the fastify-plugin benchmark task. CI tests Fastify 5.0.0 (Fastify 4 reached end of life in June 2025) and the latest Fastify.

- Security headers: every response now gets `Content-Security-Policy` (`default-src 'self'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; object-src 'none'`), `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and over HTTPS `Strict-Transport-Security: max-age=31536000; includeSubDomains` (with `trustProxy: true`, also when `X-Forwarded-Proto` is `https`). Headers a handler or middleware sets win. Change or add headers by name with `createApp({ secureHeaders: { "X-Frame-Options": "SAMEORIGIN", "Content-Security-Policy": false } })`, or send none with `secureHeaders: false`. New code IL6016 (invalid options), new type `SecureHeadersConfig`, and `describe().secureHeaders` lists the headers sent. **Breaking:** routes that return HTML pages with inline scripts or styles, or that are embedded in frames on other sites, need their own `Content-Security-Policy` (or `X-Frame-Options`) header or a `secureHeaders` change. New docs page docs/security.md.

- Express: new entry point `@browserlessapi/inferlo/express` with `inferloAI(ai)`, a middleware that puts an AI client (`createAI(...)` or an Inferlo app's `app.ai`) on every request as `req.ai`, typed through Express's `Request` (importing the entry point adds `ai` to it), and `sendResponse(res, response)`, which sends a Web `Response` with its status, every header and a streamed body, for `req.ai.stream(...).toResponse()`. It has no dependency on Express and never loads the router, database or jobs code. A whole Inferlo app mounts with `server.use("/api", toNodeHandler(app))`. IL5014 now also covers the Express middleware; new types `InferloAIMiddleware` and `ExpressRequestLike` (from the new entry point). New example examples/with-express and the express-ai-middleware benchmark task. CI tests Express 4 (newest 4.x, maintained upstream) and the latest Express.

- Graceful shutdown: `await app.close({ delayMs, timeoutMs })` for SIGTERM. `GET /ready` answers `503` at once (`checks.shutdown`, and `app.closing` is `true`) while `GET /health` stays `200`; requests are still served for `delayMs` (default 0) so load balancers can stop sending traffic; then new requests get `503` with the new code IL2006 and `Connection: close`, in-flight requests, `ctx.waitUntil` tasks and the job workers started with `app.jobs.start()` (with their running job) finish for at most `timeoutMs` (default 10000, then what is left is logged), the servers started with `app.listen()` close and the database closes. Calling it again returns the same promise. New code IL6015 (invalid options), new type `CloseOptions`. New projects turn on `health: true` (the template's own `/health` route is gone, `GET /health` now answers `{"status":"ok"}`) and call `app.close({ delayMs: 5000 })` on SIGTERM. Docs in docs/deploy.md, "Graceful shutdown".

- Health and readiness: `createApp({ health: true })` adds `GET /health` (liveness, `200 {"status":"ok"}`, no checks) and `GET /ready` (readiness, `200` or `503` with `{ status, checks }`). Built-in checks: `database` (`select 1` on Postgres, which covers the database job queue and rate limits) and `ai` (every alias points to a configured provider, without calling a model). Add your own with `health: { checks: { redis: () => redis.ping() } }`. Checks run in parallel with a timeout (`timeoutMs`, default 5000). Both endpoints are public, send `Cache-Control: no-store` and answer `HEAD`; failed checks show `"Check failed."` while the real error is logged, unless the check throws an exposed error (`httpError`) or `exposeErrors` is on. Paths are configurable (`path`, `readyPath`). New `app.checkReady()`, new code IL6014 (invalid options or a route on the same path), new types `HealthConfig`, `HealthCheck`, `CheckResult`, `ReadinessReport`; `describe().endpoints` has `health` and `ready`, and `inferlo describe` shows them. Docs in docs/deploy.md, "Health and readiness".

- Hono: new entry point `@browserlessapi/inferlo/hono` with `inferloAI(ai)`, a middleware that puts an AI client (`createAI(...)` or an Inferlo app's `app.ai`) on the Hono context as `c.var.ai`, typed with `new Hono<{ Variables: InferloVariables }>()`. It has no dependency on Hono and never loads the router, database or jobs code. A whole Inferlo app mounts with `hono.mount("/api", inferlo.fetch)` (routes, auth, OpenAPI and MCP under the path). New code IL5014 (not an AI client); new types `InferloVariables`, `InferloAIMiddleware`, `HonoContextLike`. New example examples/with-hono and the hono-ai-middleware benchmark task (benchmark tasks can now list extra `packages`). CI tests Hono 4.0.0 and the latest Hono.

- Typed configuration: `export const settings = config({ schema: t.object({ DATABASE_URL: t.string(), PORT: t.int().default(3000) }), secrets: ["DATABASE_URL"], environments: { test: { ... } } })` reads every variable once at startup, converts it to the field's type (numbers, booleans with the same words as `env.bool`, comma-separated arrays) and returns a frozen, typed object. Values come from the environment (empty counts as not set, `.env` is read by `inferlo dev`, `inferlo worker` and Bun), then from `environments[INFERLO_ENV or NODE_ENV or "development"]`, then from defaults. Secrets print as `"[redacted]"` in `JSON.stringify`, `console.log` and `String()`, and are never shown in errors. New codes IL7003 (invalid configuration, listing every problem in the message and `details.issues`) and IL7004 (invalid options); new exports `config` and types `Config`, `ConfigOptions`. New projects keep their variables in `src/config.ts`. New docs page docs/config.md.

- Mount an Inferlo app inside Node.js frameworks: `toNodeHandler(app, { prefix: "/ai" })` returns an `(req, res, next?)` handler for `node:http`, Express, Fastify (`request.raw`, `reply.raw`), NestJS and Koa. The prefix is removed before routing, so routes, `/ai/openapi.json` and `/ai/mcp` work under it; requests outside it go to `next()`. Request bodies are streamed, or taken from `req.body` when a body parser already read them; responses stream, keep every `Set-Cookie` header and are aborted when the client disconnects; the socket address is used for `rateLimit: { by: "ip" }`. `fromNodeRequest(req, { prefix, signal })` converts a Node request to a Web `Request`. `serve()` on Node now uses the same code. New exports `toNodeHandler`, `fromNodeRequest` and types `NodeRequest`, `NodeResponse`, `NodeHandler`, `NodeHandlerOptions`, `FromNodeRequestOptions`, `ServeOptions`, `Server`. New docs page docs/integrations.md.

- Docs: Inferlo is now described as "the enterprise-ready TypeScript backend framework, with AI models built in", and the roadmap adds an enterprise readiness track (modules, typed config, health checks, observability, permissions, security, API versioning, caching, Redis, performance benchmarks, microservices, support policy).

- Cursor pagination: `db.tickets.paginate({ where, orderBy: { createdAt: "desc" }, cursor, limit: 20, include })` returns `{ items, nextCursor }`. Pass `nextCursor` back as `cursor` for the next page; it is `null` on the last page. Pages are by key (the last row's value, then `id`), so they never skip or repeat rows when the list changes, on memory and Postgres. Orders by one required field (default `createdAt` ascending). New codes IL4024 (invalid cursor, status 400) and IL4025 (invalid options); new types `PaginateOptions` and `Page`. New docs section "Pagination" in docs/database.md.
- Function tools: `tool("getWeather", { description, input: t.object({ city: t.string() }) }).handle(async ({ input, signal }) => ...)` makes a tool from a plain function, for `ai.generate({ tools })` anywhere: with `createAI` from `@browserlessapi/inferlo/ai` outside `createApp`, and with `ctx.ai` next to route tools. The model's arguments are validated against `input` (invalid ones go back to the model as a 422 with IL1001), the result is sent as JSON (strings as they are), and `httpError` or any `InferloError` below 500 becomes a failed tool result; other errors reject `ai.generate` after usage is reported. New code IL5013 (invalid tool or duplicate tool names); IL5009 now only applies to route tools. New exports `tool`, `isTool`, `ToolBuilder` and types `ToolDef`, `FunctionToolOptions`, `ToolContext`, also from `@browserlessapi/inferlo/ai`, which now exports `httpError` too.
- New entry point `@browserlessapi/inferlo/ai`: the AI module on its own, for use in any framework or script without `createApp`. `import { createAI, anthropic, t } from "@browserlessapi/inferlo/ai"` gives aliases with fallback, structured output, streaming, embeddings, image input and usage tracking, and never loads the router, database or jobs code. It exports `createAI`, `cosineSimilarity`, `extractJson`, every provider, `mockProvider`, `ProviderError`, `t`, `Schema`, `ObjectSchema`, `ArraySchema`, `ValidationError`, `toJSONSchema`, `InferloError`, `env` and the AI types. See docs/ai.md, "Use it without createApp".
- Fix: `--json` CLI errors now always include `fix` and the real `message` in `error`, also for errors with a 500 status such as IL8007 and IL8008 from `inferlo worker`. Before, they went through `InferloError.toJSON()`, which hides both from API clients for server errors.

## 0.4.0 - 2026-11-04

- Cron: `export const nightly = cron("0 3 * * *", cleanupJob)` next to the job in a jobs module queues the job on a schedule while `app.jobs.start()` or `inferlo worker` runs. Five fields in UTC (numbers, `*`, ranges, lists, steps, month and weekday names). Each tick is queued once with a fixed job id, so with the database queue every instance can run the schedule; after a pause only the latest missed tick is queued. Registering a cron registers its job. The job runs with input `{}`. New code IL6013 (invalid schedule or job); new exports `cron`, `isCron` and type `CronDef`; `app.jobs.crons` and `describe().crons` list the schedules, and `inferlo describe` shows them.
- Background jobs, part 3: `inferlo worker` runs the app's jobs in their own process. It reads `.env` like `inferlo dev`, calls `app.jobs.start()`, and on SIGTERM or Ctrl+C waits for the running job, closes the database and exits 0 (a second signal exits at once); `--json` prints `started` and `stopped` events. It needs registered jobs (new code IL8007) and the database job queue (new code IL8008). New projects run jobs in `src/server.ts` with `app.jobs.start()`, stop them on SIGTERM, and have a `worker` script. `app.jobs.queue` and `describe().jobQueue` say where jobs are kept.
- Background jobs, part 2: `createApp({ jobQueue: { store: "database" } })` keeps queued jobs in the Postgres table `inferlo_jobs` (created on first use), so they survive restarts and are shared by every instance. Due jobs are claimed with `FOR UPDATE SKIP LOCKED`, so each attempt runs on one instance only, and an instance only claims jobs it has registered. A running job's worker reports every 30 seconds; a job left `"running"` for 5 minutes without a report (its process stopped) is run again as its next attempt, or marked `"failed"` when it has no attempts left. The default store stays `"memory"`. New codes IL6011 (invalid `jobQueue`) and IL6012 (database store without Postgres); new type `JobQueueConfig`.
- Background jobs, part 1: `job("send-email", { input: schema, retries: 3 }).handle(async ({ input, db, ai, jobs, attempt }) => ...)` defines a job, `createApp({ jobs: [jobs] })` registers jobs (or modules of them), and `ctx.jobs.enqueue(sendEmail, { to })` in a route handler (or `app.jobs.enqueue` anywhere) queues one with typed input, validated when queued (IL1001) and again when it runs, stored as JSON, with an optional `runAt`. Failed attempts are retried after 10s, 20s, 40s and so on (at most an hour) until the retries are used up, then the job is marked `"failed"` and logged. `app.jobs.start()` runs due jobs in the process and `stop()` waits for the running one; `app.jobs.runDue()` runs every due job once for tests, and `app.jobs.get(id)` returns a job's record. The queue is kept in memory for now; a Postgres-backed queue and `inferlo worker` come next. New codes IL6009 (invalid job) and IL6010 (job not registered); `describe()` and `inferlo describe` list jobs; route handlers get `jobs` in their context. New docs page docs/jobs.md.
- Vision input: `ai.generate({ prompt, images: [{ url: "https://..." }] })` or `images: [{ base64, mediaType: "image/png" }]` sends images to the model with the prompt, and user messages take `images` too (`messages: [{ role: "user", content, images }]`). Works with Anthropic (image blocks, `data:` URLs sent as base64), OpenAI, Gemini, Ollama and OpenAI-compatible providers (`image_url` parts), with `ai.stream`, structured output and tools. Remote URLs go to the provider unchanged; Inferlo never downloads them. Invalid images (other URL schemes, unsupported media types, invalid base64, images on non-user messages, `images` without `prompt`) raise the new code IL5012 before any model is called. New types `Image` and `ImageMediaType`; `Message` has an optional `images` field.
- Reverse (has-many) relations: `db.users.findMany({ include: { tickets: true } })` adds `user.tickets`, every row of a model whose `t.ref` field named `<name>Id` points to that user (`[]` when there are none), with one extra query per relation for all rows, ordered by `createdAt`. The relation is named after the other model's table; when that table has several ref fields to this model, each is named `<table>By<Name>` (`ticketsByOwner`, `ticketsByAssignee`) and the plain table name raises IL4023 as ambiguous. Works on `findMany`, `findOne`, `find` and `get`, together with forward relations, and is typed (`Row<typeof Ticket>[]`). New type `ReverseRelations`; `Include` takes the app's models as an optional second type parameter.
- Rate limiting: `route.post(path, { rateLimit: { max: 10, per: "minute", by: "user" | "ip" } })` answers 429 with the new code IL2005 and a `Retry-After` header once the limit is passed, and sends `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` headers. Counts are per route, per signed-in user (the default; requests without a user count by IP) or per IP, in fixed windows, kept in memory or with `createApp({ rateLimit: { store: "database" } })` in the Postgres table `inferlo_rate_limits`, shared by every instance. New `createApp({ trustProxy: true })` uses the first `X-Forwarded-For` address as the client IP behind a proxy. Invalid options raise IL6007 and the database store without Postgres raises IL6008. `describe()` and OpenAPI show the limit. The new app template limits the AI summary route to 20 calls per hour per user.
- Relations: `db.tickets.findMany({ include: { owner: true } })` loads the row each `t.ref` field points to, for every field named `<name>Id` (`ownerId` gives `owner`), with one extra query per relation for all rows (no N+1). Results are typed (`tickets[0].owner` is `Row<typeof User>`, or `| null` for optional and nullable refs). `find`, `get` and `findOne` take `{ include }` as a new optional second argument. Unknown relation names raise the new code IL4023. `t.ref()` now returns a `RefSchema` that keeps the table name in its type; new types `Include`, `Relations`, `WithInclude`, `FindOptions`.
- Tool calling: `ctx.ai.generate({ prompt, tools: [createTicket, getTicket], maxSteps: 5 })` lets the model call your routes as tools. Each call runs as an HTTP request to the route as the current user, so auth, roles and validation apply; errors (403, 404, 422) go back to the model so it can correct itself. Works with Anthropic, OpenAI, Gemini and OpenAI-compatible providers. The result has a new `steps` list with every model call, its tool calls (`name`, `input`, `status`, `output`, `isError`) and usage; `usage` has the totals. `allow` is checked again before each model call that follows tool calls, and once a tool has run Inferlo does not fall back to another model (IL5006). New codes: IL5009 (tools outside a route handler), IL5010 (step limit reached), IL5011 (tool is not a registered route). `Message` has optional `toolCalls`, `toolCallId` and `isError` fields and a `"tool"` role, `ProviderRequest` has `tools`, and `mockProvider` can return `{ toolCalls }`. New types: `ToolCall`, `ToolSpec`, `ToolCallResult`, `Step`, `MockReply`.
- `inferlo db migrate --allow-change` now also generates column type changes, for example `t.string().max(120)` to `.max(200)`, `t.text()` to `t.int()` or `t.int()` to `t.number()`: `ALTER TABLE "posts" ALTER COLUMN "title" TYPE varchar(200)`, with a strict `USING` clause when Postgres needs one (other types go through their text, jsonb through its JSON text, and a field becoming `t.json()` through `to_jsonb`). A fixed default is dropped before the change and set again after it. Without the flag these changes are refused with IL4019 (they were IL4013). Values are never cut, rounded or set to NULL: if `--apply` finds one that does not convert, it fails with the new code IL4022, naming the columns and the value, and nothing from that migration is kept. IL4013 now only covers renames, reference and index changes.
- `inferlo db migrate --allow-change` now also generates enum value changes: adding or removing values of a `t.enum` field, or turning a text field into an enum or back, replaces the column's CHECK constraint (`ALTER TABLE ... DROP CONSTRAINT "posts_kind_check"`, then `ADD CONSTRAINT "posts_kind_check" CHECK (...)`, with the name Postgres gave it). Without the flag these changes are refused with IL4019 (they were IL4013). If `--apply` finds rows that still use a removed value, it fails with the new code IL4021, naming the table and constraint, and nothing from that migration is kept.
- CI also tests Node.js 26, the newest LTS line.
- Docs: the framework and app AGENTS.md files now say error codes are `ILxxxx` (they still said `KRxxxx`).

## 0.3.0 - 2026-11-02

- **Breaking: Kairo is now Inferlo.** The npm package is `@browserlessapi/inferlo` (was `@browserlessapi/kairo`), the CLI is `inferlo` (was `kairo`), the GitHub repository is `BrowserlessAPI/Inferlo`, and error codes start with `IL` instead of `KR` (same numbers: KR1001 is now IL1001). `KairoError` is now `InferloError`, `KAIRO_VERSION` is `INFERLO_VERSION`, and `describe()` reports the version as `inferlo`. Environment variables for tests and the benchmark start with `INFERLO_`. To upgrade, replace the package name in imports and package.json, `kairo` with `inferlo` in scripts, and `KR` with `IL` where you match error codes.
- Existing projects keep working: `inferlo db migrate --apply` renames an existing `kairo_migrations` table to `inferlo_migrations` (history is kept), snapshots with the old `"kairo"` key are read, and the `"kairo"` section in package.json is still read for `entry` and `server`.

- Breaking: the minimum supported Bun version is now 1.3.0. Bun 1.2 releases skip or misorder `node:test` subtests, so Inferlo's test suite cannot verify them.

- CI tests every supported version at both ends: Node.js 22.18, 22, 24 and current; Bun 1.3.0 and latest; PostgreSQL 14 to 18 and latest; TypeScript 5.9 and latest. A weekly run catches new upstream releases.

- `inferlo db migrate --allow-change` generates default and required/optional changes of existing columns (`ALTER COLUMN ... SET DEFAULT`, `DROP DEFAULT`, `SET NOT NULL`, `DROP NOT NULL`). Making a column required with a fixed default first fills NULL rows with it. Without the flag these changes are refused with the new code IL4019 (they were IL4013) and nothing is written. If `--apply` hits NULL rows in a column made required, it fails with the new code IL4020, naming the table and column. Also available as `planMigration(models, snapshot, { allowChange: true })`; the plan now includes `changes`, and `--json` output has a `changes` list. IL4013 now covers type, enum value, reference and index changes.
- `migrations/snapshot.json` now describes each column as a structured object (`{ type, notNull, default?, enum?, references?, primaryKey? }`, format `"inferlo": 2`) instead of its SQL text. Snapshots written by 0.2.0 (`"inferlo": 1`) are read and upgraded automatically, and saved in the new format with the next generated migration. IL4013 now says what changed in each column (for example `change column posts.title (type varchar(120) -> varchar(200))`) and lists it in `details.columns`. Types: `MigrationSnapshot` is the new format; `MigrationSnapshotV1` (the old one) and `MigrationSnapshotColumn` are new exports, and `planMigration` accepts either format.
- `inferlo db migrate --apply` records a SHA-256 checksum of each migration file in `inferlo_migrations` and warns with the new code IL4018 when a file that was already applied has been edited since (it is not run again; pending files are still applied). `--json` output has a new `edited` list, and `applyMigrations(db, migrations, { onEdited })` reports the names. Line ending changes do not count as edits. Existing `inferlo_migrations` tables get a `checksum` column automatically, filled from the current files on the next run.
- `inferlo db migrate --allow-drop` generates drops of removed tables, columns and indexes (`DROP TABLE`, `ALTER TABLE ... DROP COLUMN`, `DROP INDEX`, never `CASCADE`), with a warning comment in the file. Without the flag, drops are refused with the new code IL4017 and nothing is written. Also available as `planMigration(models, snapshot, { allowDrop: true })`; the plan now includes `drops`, and `--json` output has a `drops` list. IL4013 now only covers column and index changes.
- Docs: Inferlo is now described as "the TypeScript backend framework with built-in AI model support", with a new "AI models built in" section in the README.
