# Changelog

All notable changes are listed here. Inferlo follows [semantic versioning](https://semver.org); until 1.0, minor versions may include breaking changes, always listed under "Breaking".

## Unreleased

- Performance benchmark (performance, part 1): `npm run bench:perf` (bench/perf/run.ts) measures throughput and latency of Inferlo, Fastify, Hono, Express and NestJS on the same two routes (a JSON answer and a validated JSON body), each in its own Node.js process, with autocannon after a warm-up. Every server is checked for correct answers and for rejecting an invalid body before it is measured, also in CI (test/perf-servers.test.ts). New page docs/performance.md with the method and the first results, which show Inferlo at the level of Express and NestJS and behind Fastify and Hono; the next roadmap items close that gap and add a regression check in CI.

- Cloudflare Workers: `export default app` is now tested in workerd, the Cloudflare Workers runtime, through Miniflare. With the `nodejs_compat` flag and a compatibility date of 2025-04-01 or later, Worker vars and secrets reach `config()` and `env()` at module level; `ctx.waitUntil` hands work to the Worker's execution context; and the AI module (`ctx.ai`, `createAI`) calls providers with `fetch`, streamed answers included. Fix: on Workers, `rateLimit: { by: "ip" }` now uses the `CF-Connecting-IP` header Cloudflare sets, instead of counting every caller as `"unknown"`. A Cloudflare Workers section in docs/integrations.md and docs/deploy.md, example examples/with-cloudflare-workers (with `wrangler.jsonc`) and the cloudflare-worker benchmark task. CI tests Miniflare 4.20250405.0 (the first Miniflare 4 release, workerd from April 2025) and the latest Miniflare.

- Redis job queue (Redis, part 2): `createApp({ redis, jobQueue: { store: "redis" } })` keeps background jobs in Redis, shared by every instance and by `inferlo worker`, with the guarantees of the database queue. Each due job is claimed by one atomic Lua script, so each attempt runs on exactly one instance; an instance only claims the jobs it has registered; failed attempts are retried with backoff; a running job whose worker has not reported for 5 minutes is claimed again (or failed without attempts left), judged by the Redis server's clock so instances with different clocks agree; and cron ticks are queued once across instances. Pending and running jobs never expire; finished jobs are kept for 7 days. The job's trace (with `createApp({ tracing })`) is stored with it. `jobQueue: { store: "redis" }` without `createApp({ redis })` raises IL6031. `inferlo worker` now also accepts the Redis queue (IL8008 says it needs a shared queue). `app.jobs.queue`, `JobQueueConfig.store` and `describe().jobQueue` can now be `"redis"`. Docs in jobs.md and redis.md ("Job queue"), and the redis-job-queue benchmark task. The Redis CI jobs run the job queue tests on Redis 6.2, 7.2 and latest.

- Redis cache store (caching, part 3): `createApp({ redis, cache: { store: "redis" } })` keeps `ctx.cache`, `app.cache` and cached route responses in Redis, shared by every instance. Each entry is one key with its `ttlMs` as the Redis expiry; each tag is a set of its entries, and `cache.invalidate(tag)` removes them in one atomic script on every instance. `cache.clear()` removes only the app's own keys, walking them with `SCAN`. `cache: { store: "redis" }` without `createApp({ redis })` raises IL6031. `Cache.store` and `describe().cache` can now be `"redis"`. The Redis CI jobs run the cache tests on Redis 6.2, 7.2 and latest.

- Google Cloud Run functions: `functions.http("inferlo", toNodeHandler(app))` with `@google-cloud/functions-framework` serves a whole Inferlo app from one HTTP function. Fix: `toNodeHandler` and `fromNodeRequest` now use `req.rawBody` (the exact bytes the Functions Framework and Firebase keep after parsing the body) when the host already parsed the body, so JSON keeps its exact text and urlencoded forms keep their content type; before, a parsed form reached the app re-encoded as JSON. A Google Cloud Run functions section in docs/integrations.md and docs/deploy.md, example examples/with-cloud-run-functions and the cloud-run-function benchmark task. CI tests Functions Framework 4.0.0 and the latest release.

- Redis (part 1): `createApp({ redis })` takes a connected client from the `redis` package (`await createClient({ url }).connect()`, node-redis 5 or newer; ioredis through a one-line `sendCommand` wrapper), and `rateLimit: { store: "redis" }` keeps route rate limit counts in it, shared by every instance. Each hit is one atomic Lua script, so concurrent requests on different instances count exactly, and Redis expires each window's key. With `health: true`, `/ready` has a built-in `redis` check that sends `PING`. Keys start with `inferlo:<app name>:`. Inferlo has no dependency on a Redis package and never closes the client. New code IL6031, new type `RedisClient`, a new docs page docs/redis.md, and the redis-rate-limit benchmark task. CI tests Redis 6.2 (the oldest version supported upstream), 7.2 and the latest release, and the `redis` package 5.0.0 and the latest release; the Node.js jobs run the Redis tests too. A custom readiness check can no longer be named `redis` when `createApp({ redis })` is set (IL6014).

- Azure Functions: new entry point `@browserlessapi/inferlo/azure`. `azure.http("inferlo", { route: "{*path}", methods: [...], authLevel: "anonymous", handler: toAzureHandler(app, { prefix: "/api" }) })` runs a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) in an HTTP trigger of the Azure Functions Node.js programming model v4. `prefix` removes Azure's `/api` route prefix; the app sees the caller's scheme and host, and query strings, headers, cookies and binary bodies arrive unchanged. Every `Set-Cookie` is returned in the response's `cookies` list (Azure keeps only one `Set-Cookie` header), `rateLimit: { by: "ip" }` uses the address the Azure front end adds to `X-Forwarded-For`, and with `azure.setup({ enableHttpStream: true })` answers, AI streams included, are streamed as the app writes them. No runtime dependency on `@azure/functions`. New code IL5026, new types `AzureHttpHandler`, `AzureHandlerOptions`, `AzureHttpRequest`, `AzureHttpResponseInit` and `AzureCookie`, an Azure Functions section in docs/integrations.md and docs/deploy.md, example examples/with-azure and the azure-function benchmark task. CI tests `@azure/functions` 4.3.0 (the first v4 release with HTTP streams) and the latest release.

## 0.6.0 - 2026-11-05

- OpenTelemetry spans for jobs (observability, part 4b). With `createApp({ tracing: { api: otel } })`, a job enqueued in a traced request or job stores that trace (W3C `traceparent` and `tracestate`) and every attempt runs in a consumer span `process <job name>` whose parent is the request's span, also when another instance runs it from the database queue. The span is active while the handler runs, so the job's queries and AI calls nest under it. Attributes `messaging.system` (`inferlo`), `messaging.operation.type` (`process`), `messaging.destination.name` (the job name), `messaging.message.id` (the job id), `inferlo.job.attempt` and `inferlo.job.outcome`; failed attempts set the error status, record the exception and set `error.type`. Cron ticks and jobs enqueued outside a trace start a new trace. Job records have a new optional `trace` field (new type `JobTraceContext`), and the database queue adds the `traceparent` and `tracestate` columns to `inferlo_jobs` (existing tables get them on first use). Docs in observability.md ("Jobs") and the job-tracing benchmark task.

- hapi: new entry point `@browserlessapi/inferlo/hapi` with `inferloPlugin`. `await server.register({ plugin: inferloPlugin, options: { ai } })` puts an AI client (`createAI(...)` or an Inferlo app's `app.ai`) on the server as `server.ai` and on every request as `request.ai`, typed through hapi's `Server` and `Request`. `await server.register({ plugin: inferloPlugin, options: { app }, routes: { prefix: "/api" } })` serves a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) under hapi's own route prefix, or, without one, for every path hapi has no route for. Inferlo reads the body itself and AI streams pass through. No runtime dependency on hapi. New code IL5025, new types `InferloPlugin` and `InferloPluginOptions` from the hapi entry point, a hapi section in docs/integrations.md, example examples/with-hapi and the hapi-plugin benchmark task. CI tests hapi 21.1.0 (the first hapi 21 release with its own TypeScript types) and the latest hapi; its tests run over real connections, also on Bun 1.3.0, where hapi's `server.inject` returns empty answers.

- OpenTelemetry spans for AI calls and database queries (observability, part 4a). With `createApp({ tracing: { api: otel } })`, every `ai.generate`, `ai.stream` and `ai.embed` call gets a client span under the active span (`chat claude-haiku-4-5`, `embeddings ...`) with the OpenTelemetry GenAI attributes `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model` (the model that answered, also after a fallback), `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens`, plus `inferlo.ai.model` (the alias), `inferlo.ai.cost_usd` and `inferlo.ai.steps`; failed calls set the error status and `error.type` to the error code. Prompts, answers and the `for` id are never recorded. Tools the model calls run inside the AI span, and a stream's span ends with the stream (`inferlo.ai.cancelled` when the reader stopped early). `createAI({ ..., tracing: { api: otel } })` does the same without an app. Database queries made while a request or job is traced get client spans (`SELECT tickets`) with `db.system.name`, `db.operation.name` and `db.collection.name`, and raw SQL (also Inferlo's rate limit, cache and job queue queries) the parameterised statement in `db.query.text`; values are never recorded, and queries outside a trace (startup, worker polling) are not traced. New option `tracing` on `AIConfig`, the types `TracingConfig`, `OtelApi` and `OtelSpan` also exported from `@browserlessapi/inferlo/ai`, IL6030 also covers `createAI`, docs in observability.md ("AI calls" and "Database queries") and ai.md, and the ai-tracing benchmark task.

- AWS Lambda: new entry point `@browserlessapi/inferlo/lambda`. `export const handler = toLambdaHandler(app)` runs a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) for Lambda function URL and API Gateway events, HTTP API (payload format 2.0) and REST API (payload format 1.0), and answers in the format of the event. Query strings, multi-value headers, cookies and base64 bodies reach the app as a normal `Request`, every `Set-Cookie` is returned on its own, binary answers are base64 encoded, and the caller's source IP is used for rate limits by IP. `prefix` removes an HTTP API stage or other path. `toLambdaHandler(app, { streaming: true })` streams answers, AI streams included, with Lambda response streaming for function URLs (`RESPONSE_STREAM`). No dependency on the AWS SDK or any Lambda package. New code IL5024, new types `LambdaHandler`, `LambdaStreamingHandler`, `LambdaHandlerOptions`, `LambdaHttpEvent`, `LambdaHttpEventV1`, `LambdaHttpEventV2`, `LambdaResult`, `LambdaResultV1`, `LambdaResultV2`, `LambdaResponseStream` and `AwsLambdaGlobal`, an AWS Lambda section in docs/integrations.md and docs/deploy.md, example examples/with-lambda (a buffered and a streaming handler and an AWS SAM template) and the lambda-handler benchmark task. Lambda's `nodejs22.x` and `nodejs24.x` runtimes are covered by the Node.js 22 and 24 CI jobs.

- OpenTelemetry tracing (observability, part 3): `createApp({ tracing: { api: otel } })` with `import * as otel from "@opentelemetry/api"` gives every request a server span named after its route (`GET /tickets/:id`) with the standard HTTP attributes, continues the caller's trace from `traceparent` (through the propagator your SDK registers), runs the handler inside the span so your spans and instrumentations nest under it, sets the error status and records the exception for 5xx answers, and adds `traceId` and `spanId` to the request's log entries. Health, readiness and metrics endpoints are not traced. No dependency: `@opentelemetry/api` 1.3 or newer is an optional peer dependency, and without an SDK nothing is recorded. New option `tracing`, types `TracingConfig`, `OtelApi` and `OtelSpan`, code IL6030, docs in observability.md, the otel-tracing benchmark task and a CI job for `@opentelemetry/api` 1.3.0 and the latest version.

- React Router (Remix): new entry point `@browserlessapi/inferlo/react-router`. In a splat resource route (`route("api/*", "routes/api.ts")`), `export const { loader, action } = toReactRouterHandlers(app, { prefix: "/api" })` serves a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) with the prefix removed from the path: GET and HEAD reach the loader, POST, PUT, PATCH, DELETE and OPTIONS the action, and the answer is the app's own `Response`, AI streams included. `@browserlessapi/inferlo/ai` works in other loaders and actions from a `.server.ts` module. No runtime dependency on React Router. New code IL5023, a React Router section in docs/integrations.md, example examples/with-react-router, the react-router-resource-route benchmark task and a CI job for React Router 7 (newest 7.x) and the latest React Router (8), tested with React Router's own data router.

- Cookie sessions with CSRF protection (security hardening, part 4): `export const session = sessions({ secret: settings.SESSION_SECRET, user: ({ userId }, { db }) => db.users.find(userId) })` and `createApp({ auth: session })`. `await session.signIn(ctx, user.id)` in a login route sets a signed (HMAC-SHA256), `HttpOnly`, `Secure`, `SameSite=Lax` session cookie and a readable CSRF cookie and returns `{ csrfToken }`; `session.signOut(ctx)` clears both. POST, PUT, PATCH and DELETE requests with a session cookie must send the token in an `X-CSRF-Token` header or a `_csrf` form field (`await session.csrfToken(req)`), or get 403 IL3005 before the handler runs. No session table: `user({ userId, issuedAt }, { db })` loads the user on every request and can end sessions by returning null. Options `maxAgeMs` (default 7 days), `cookie: { name, sameSite, secure, domain, path }` and secret rotation with `secret: [newSecret, oldSecret]`. Also: `ctx.header("set-cookie", ...)` now adds a cookie instead of replacing the previous one (also on a returned `Response`), the `_csrf` field is removed from form bodies before validation, and CORS preflights allow `X-CSRF-Token` by default. New exports `sessions` and the types `Sessions`, `SessionsOptions`, `SessionData`, `SessionCookieOptions` and `SessionResponseContext`, codes IL3005 and IL6029, docs in auth.md and security.md, a rule in the app AGENTS.md and the cookie-sessions benchmark task.

- SvelteKit: new entry point `@browserlessapi/inferlo/sveltekit`. In a rest route, `export const { GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS, fallback } = toSvelteKitHandlers(app, { prefix: "/api" })` (in `src/routes/api/[...path]/+server.ts`) serves a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) with the prefix removed from the path; `fallback` takes every other method. Requests outside the prefix keep their path, bodies and AI streams pass through, and the adapter's client address (`event.getClientAddress()`) is used for rate limits by IP. `export const handle = inferloAI(ai)` in `src/hooks.server.ts` (or inside `sequence(...)`) puts an AI client on every request as `event.locals.ai` for load functions, form actions and endpoints, typed through SvelteKit's `App.Locals`. No runtime dependency on SvelteKit. New code IL5022, a SvelteKit section in docs/integrations.md, example examples/with-sveltekit, the sveltekit-rest-route benchmark task and a CI job for SvelteKit 2 (newest 2.x) and the latest SvelteKit (3).

- Response caching (caching, part 2): the route option `cache: { ttlMs: 60_000, by: "user" | "public", tags: ["tickets"] }` caches a GET route's JSON responses in the app cache, so the handler runs once per entry. `by: "user"` (the default) keeps one response per signed-in user, `"public"` one for every caller. Auth, roles, permissions, rate limits and the `query` and `params` schemas still run on every request; the key includes the full path and query string. Only 200 answers the handler returned as a value are cached, with the headers the handler set itself, never one that sets a cookie or returns a `Response`. Responses carry `X-Inferlo-Cache: HIT` or `MISS`, an `ETag` (`If-None-Match` gets 304), `Cache-Control: private, no-cache` (or `public, no-cache` for public data on public routes, unless the handler sets its own) and, per user, `Vary: Authorization, Cookie`. `ctx.cache.invalidate(tag)` removes cached responses at once. Invalid options and `cache` on other methods raise IL6028 at startup. New type `RouteCache`; `describe()`, `inferlo describe` and OpenAPI (`x-inferlo-cache`) show each route's cache. Docs in docs/caching.md, "Caching route responses", and the cached-route benchmark task.

- Nuxt, Nitro and h3: new entry point `@browserlessapi/inferlo/h3`. `export default toH3Handler(app, { prefix: "/api" })` in a catch-all server route (`server/routes/api/[...path].ts`, or Nuxt's `server/api/[...path].ts`) serves a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) with the prefix removed from the path; requests outside it keep their path, Inferlo reads the body itself and AI streams pass through. It works on h3 1 (Nitro 2, Nuxt 3 and 4), where it is marked as an event handler, and on h3 2 (Nitro 3), without `defineEventHandler` or `fromWebHandler`. `export default defineNitroPlugin(inferloAI(ai))` in `server/plugins/ai.ts` puts an AI client (`createAI(...)` or an Inferlo app's `app.ai`) on every request as `event.context.ai`, typed through h3's `H3EventContext`. No runtime dependency on h3, Nitro or Nuxt. IL5014 now also covers the Nitro plugin; new code IL5021 (not an app, a prefix that does not start with `/`, or a call without an h3 event); new types `H3Handler`, `H3HandlerOptions`, `H3EventLike` and `NitroPlugin`. A Nuxt, Nitro and h3 section in docs/integrations.md, example examples/with-nitro (a catch-all route, a plugin and a server route using `event.context.ai`) and the nitro-server-route benchmark task. CI tests h3 1 (newest 1.x, used by Nitro 2 and Nuxt) and the latest h3.

- Caching (part 1): every app has a cache, `ctx.cache` in routes and jobs and `app.cache` everywhere else. `await cache.getOrSet("tickets:stats", { ttlMs: 60_000, tags: ["tickets"] }, compute)` returns the cached value or stores the result of `compute()` (concurrent calls for one key in a process share one `compute()`; nothing is stored when it throws), and `await cache.invalidate("tickets")` removes every entry with that tag after a change. Also `get`, `set`, `delete` and `clear`. Every entry needs `ttlMs` (1 ms to 365 days), values are stored as JSON (dates come back as ISO strings, also from the first `getOrSet`), and keys are 1 to 512 characters. `createApp({ cache: { store: "memory" } })` (the default, least recently used entries removed after `maxEntries`, default 10000) keeps entries in the process; `{ store: "database" }` keeps them in the `inferlo_cache` table of the app's Postgres database (created on first use), shared by every instance. New code IL6028 (invalid cache options, key, ttl, tags or value), new types `Cache`, `CacheConfig` and `CacheSetOptions`, `describe().cache`, and `inferlo describe` shows the store. New docs page docs/caching.md, a rule in the app AGENTS.md and the cache-stats benchmark task. Per-route response caching and a Redis store follow.

- Fastify fallthrough and a migration guide from Fastify: `await fastify.register(inferloPlugin, { app, fallthrough: true })` from `@browserlessapi/inferlo/fastify` answers only the requests the Inferlo app has a route for (method and path) and its own endpoints (OpenAPI, MCP, health, metrics, CORS preflights), from an `onRequest` hook before Fastify reads the body, and leaves every other request to Fastify's routes and 404 handler, also other methods on a path the app has. The prefix is optional with it; with a prefix only the app's routes under it are answered. Invalid `fallthrough` raises IL5015, and an app that is not from `createApp` IL5019. New guide docs/migrate-from-fastify.md moves a Fastify 5 app to Inferlo one route at a time with every URL unchanged: it ports a route with a JSON schema, a TypeScript type and a `preHandler` auth hook, maps Fastify concepts and plugins (encapsulation, `fastify-plugin`, decorators, hooks, error and not-found handlers, type providers, `@fastify/jwt`, `@fastify/auth`, `@fastify/cors`, `@fastify/helmet`, `@fastify/rate-limit`, `@fastify/env`, `@fastify/swagger`, `@fastify/under-pressure`, Pino, `fastify.inject`) to Inferlo, shares one auth check and ends with removing Fastify. A new test checks the recommended setup in the Fastify CI job on Fastify 5.0.0 and the latest Fastify, and the fastify-fallthrough benchmark task exercises it.

- Docs: new guide docs/migrate-from-koa.md. It moves a Koa app (Koa 2 or 3) to Inferlo one route at a time in the same process with every URL unchanged: `koa.use(toKoaMiddleware(inferlo, { fallthrough: true }))` before the Koa router answers the moved routes and passes everything else on. It ports a `@koa/router` route with hand-written checks and auth middleware, maps Koa concepts and packages (`ctx.body`, `ctx.throw`, `ctx.state`, error middleware, koa-jwt, koa-passport, body parsers, @koa/cors, koa-helmet, koa-ratelimit, koa-logger, koa-mount, Swagger packages, supertest) to Inferlo, shares one auth check between both, and ends with removing Koa. A new test checks the recommended setup in the Koa CI job on Koa 2 and the latest Koa.

- Audit log (permissions, part 2): add the built-in `AuditLog` model to `createApp({ models })` (the `audit_log` table, created by `inferlo db migrate`) and call `await audit("tickets.update", { model: "tickets", before: ticket, after: updated })` in a route or job. Each entry records the action, the signed-in user (jobs pass `userId`, or none for system work), the model and record id (defaulting to `after.id` or `before.id`), the changed fields as `{ field: { from, to } }` (creates and deletes too; `id`, `createdAt` and `updatedAt` skipped, dates as ISO strings), optional `data`, the source (`"PATCH /tickets/:id"` or `"job export-tickets"`) and the request id. Changed fields named like passwords, tokens, secrets, API keys, hashes, sessions or cookies are stored as `"[redacted]"`, the same names in `data` are redacted, and `createApp({ redact })` values and AI provider keys are replaced in any string. New `ctx.audit` in routes and jobs, new exports `AuditLog` and `auditChanges`, new types `Audit`, `AuditEntry` and `AuditChange`, and new code IL6027 (no `AuditLog` model, an empty action or an invalid entry). Docs in docs/auth.md, "Audit log", a rule in the app AGENTS.md and the audit-log benchmark task.

- Next.js: new entry point `@browserlessapi/inferlo/nextjs`. In an App Router catch-all route, `export const { GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS } = toNextHandlers(app, { prefix: "/api" })` (in `app/api/[[...path]]/route.ts`) serves a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) with the prefix removed from the path; requests outside it keep their path, and request bodies and AI streams pass through unchanged. `@browserlessapi/inferlo/ai` works in server actions and server components. No runtime dependency on Next.js. New code IL5020 (not an app, or a prefix that does not start with `/`), new types `NextHandlers`, `NextHandlersOptions` and `NextRouteHandler`, a Next.js section in docs/integrations.md, example examples/with-nextjs (route handlers and a server action) and the nextjs-route-handlers benchmark task. CI tests Next.js 15 (newest 15.x, still maintained upstream) and the latest Next.js with Next.js's own `NextRequest`.

- Permissions (part 3): add `permissions: typeof access` to `Register` and the route option `permission` only accepts the names of rules that need nothing but `{ user }` (roles rules and functions of the user alone), so a misspelled name, or a rule that also needs a record, is a type error. Without it, `permission` still takes any string and `createApp` checks it at startup. New exported type `AppPermission`. MCP `tools/list` now leaves out tools whose role (`auth: "admin"`) or `permission` the caller does not have, so AI agents only see tools they may call; tools that only need sign-in stay listed for anonymous callers, `tools/call` checks every call as before, and a rule that throws while listing hides its tool. The helpdesk example registers its permissions, docs in docs/auth.md, "Typed permission names", and the typed-permissions benchmark task.

- Koa: new entry point `@browserlessapi/inferlo/koa`. `koa.use(inferloAI(ai))` puts an AI client (`createAI(...)` or an Inferlo app's `app.ai`) on every context as `ctx.ai`, typed through Koa's `DefaultContext`. `koa.use(toKoaMiddleware(app, { prefix: "/api" }))` runs a whole Inferlo app (routes, auth, validation, OpenAPI and MCP) under a path and passes other requests to the next middleware; with `fallthrough: true` it answers only the app's routes, so routes move from Koa one at a time at the same URLs. A body a Koa body parser already read (`ctx.request.body`) is used. `sendResponse(ctx, response)` streams a Web Response, such as an AI stream. No runtime dependency on Koa. IL5014 now also covers the Koa middleware, and invalid `toKoaMiddleware` options raise IL5019. New types `KoaContextLike` and `KoaMiddleware`, example examples/with-koa and the koa-mount benchmark task. CI tests Koa 2 (newest 2.x) and the latest Koa.

- Permissions (part 1): `permissions({ "reports.view": { roles: ["admin", "analyst"] }, "tickets.update": ({ user, ticket }) => ticket.ownerId === user.id })` defines named permissions once. `await access.can(name, { user, ticket })` returns true or false and `await access.authorize(name, { user, ticket })` throws IL3004 (403), or IL3001 (401) without a user, the same in routes, AI tools and jobs; the input is typed from the rule. Deny by default: no user, an unknown name or a rule that does not return true or false never allows. With `createApp({ permissions: access })`, the route option `permission: "reports.view"` is checked with `{ user }` before the handler, also when a model calls the route as a tool; `createApp` checks every route's permission at startup. `describe()` has `permissions` and each route's `permission`, `inferlo describe` shows them, and OpenAPI adds `x-inferlo-permission` and a 403 response. New codes IL3004 (permission denied) and IL6026 (invalid permissions), new exports `permissions`, `isPermissions` and the types `Permissions`, `PermissionRule` and `PermissionInput`. Docs in docs/auth.md, "Permissions", a rule in the app AGENTS.md and the note-permissions benchmark task.

- Encore.ts: an Encore raw endpoint serves a whole Inferlo app (routes, auth, validation, rate limits, OpenAPI and MCP) with `api.raw({ expose: true, method: "*", path: "/inferlo/*rest" }, toNodeHandler(app, { prefix: "/inferlo" }))`, or every path Encore has no endpoint for with Encore's fallback path `/!rest`, and `createAI` from `@browserlessapi/inferlo/ai` works in Encore services with the API key from an Encore secret. No new entry point and no dependency on Encore. New example examples/with-encore, whose tests run its endpoints with the real encore.dev package and Encore's own raw request and response classes, an Encore.ts section in docs/integrations.md and the encore-raw-endpoint benchmark task. CI tests encore.dev 1.51.0 and the latest encore.dev.

- Fix: `toNodeHandler` and `fromNodeRequest` only use `req.body` instead of the request stream when it holds a body a parser already read (a string, bytes, or a plain object or array). Before, any `req.body` was used, so a request whose `body` field is the host's own object, such as the body reader of an Encore raw request, reached the app as `{}` and failed validation.

- Cron: `export const nightly = cron("0 3 * * *", cleanupJob)` next to the job in a jobs module queues the job on a schedule while `app.jobs.start()` or `inferlo worker` runs. Five fields in UTC (numbers, `*`, ranges, lists, steps, month and weekday names). Each tick is queued once with a fixed job id, so with the database queue every instance can run the schedule; after a pause only the latest missed tick is queued. Registering a cron registers its job. The job runs with input `{}`. - Background jobs, part 3: `inferlo worker` runs the app's jobs in their own process. It reads `.env` like `inferlo dev`, calls `app.jobs.start()`, and on SIGTERM or Ctrl+C waits for the running job, closes the database and exits 0 (a second signal exits at once); `--json` prints `started` and `stopped` events. It needs registered jobs (new code IL8007) and the database job queue (new code IL8008). New projects run jobs in `src/server.ts` with `app.jobs.start()`, stop them on SIGTERM, and have a `worker` script. `app.jobs.queue` and `describe().jobQueue` say where jobs are kept.
- Background jobs, part 2: `createApp({ jobQueue: { store: "database" } })` keeps queued jobs in the Postgres table `inferlo_jobs` (created on first use), so they survive restarts and are shared by every instance. Due jobs are claimed with `FOR UPDATE SKIP LOCKED`, so each attempt runs on one instance only, and an instance only claims jobs it has registered. A running job's worker reports every 30 seconds; a job left `"running"` for 5 minutes without a report (its process stopped) is run again as its next attempt, or marked `"failed"` when it has no attempts left. The default store stays `"memory"`. New codes IL6011 (invalid `jobQueue`) and IL6012 (database store without Postgres); new type `JobQueueConfig`.
- Background jobs, part 1: `job("send-email", { input: schema, retries: 3 }).handle(async ({ input, db, ai, jobs, attempt }) => ...)` defines a job, `createApp({ jobs: [jobs] })` registers jobs (or modules of them), and `ctx.jobs.enqueue(sendEmail, { to })` in a route handler (or `app.jobs.enqueue` anywhere) queues one with typed input, validated when queued (IL1001) and again when it runs, stored as JSON, with an optional `runAt`. Failed attempts are retried after 10s, 20s, 40s and so on (at most an hour) until the retries are used up, then the job is marked `"failed"` and logged. `app.jobs.start()` runs due jobs in the process and `stop()` waits for the running one; `app.jobs.runDue()` runs every due job once for tests, and `app.jobs.get(id)` returns a job's record. - Vision input: `ai.generate({ prompt, images: [{ url: "https://..." }] })` or `images: [{ base64, mediaType: "image/png" }]` sends images to the model with the prompt, and user messages take `images` too (`messages: [{ role: "user", content, images }]`). New types `Image` and `ImageMediaType`; `Message` has an optional `images` field.
- Reverse (has-many) relations: `db.users.findMany({ include: { tickets: true } })` adds `user.tickets`, every row of a model whose `t.ref` field named `<name>Id` points to that user (`[]` when there are none), with one extra query per relation for all rows, ordered by `createdAt`. The relation is named after the other model's table; when that table has several ref fields to this model, each is named `<table>By<Name>` (`ticketsByOwner`, `ticketsByAssignee`) and the plain table name raises IL4023 as ambiguous. Works on `findMany`, `findOne`, `find` and `get`, together with forward relations, and is typed (`Row<typeof Ticket>[]`). New type `ReverseRelations`; `Include` takes the app's models as an optional second type parameter.
- Rate limiting: `route.post(path, { rateLimit: { max: 10, per: "minute", by: "user" | "ip" } })` answers 429 with the new code IL2005 and a `Retry-After` header once the limit is passed, and sends `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` headers. Counts are per route, per signed-in user (the default; requests without a user count by IP) or per IP, in fixed windows, kept in memory or with `createApp({ rateLimit: { store: "database" } })` in the Postgres table `inferlo_rate_limits`, shared by every instance. New `createApp({ trustProxy: true })` uses the first `X-Forwarded-For` address as the client IP behind a proxy. Invalid options raise IL6007 and the database store without Postgres raises IL6008. `describe()` and OpenAPI show the limit. The new app template limits the AI summary route to 20 calls per hour per user.
- Relations: `db.tickets.findMany({ include: { owner: true } })` loads the row each `t.ref` field points to, for every field named `<name>Id` (`ownerId` gives `owner`), with one extra query per relation for all rows (no N+1). Results are typed (`tickets[0].owner` is `Row<typeof User>`, or `| null` for optional and nullable refs). `find`, `get` and `findOne` take `{ include }` as a new optional second argument. Unknown relation names raise the new code IL4023. `t.ref()` now returns a `RefSchema` that keeps the table name in its type; new types `Include`, `Relations`, `WithInclude`, `FindOptions`.
- Tool calling: `ctx.ai.generate({ prompt, tools: [createTicket, getTicket], maxSteps: 5 })` lets the model call your routes as tools. Each call runs as an HTTP request to the route as the current user, so auth, roles and validation apply; errors (403, 404, 422) go back to the model so it can correct itself. Works with Anthropic, OpenAI, Gemini and OpenAI-compatible providers. The result has a new `steps` list with every model call, its tool calls (`name`, `input`, `status`, `output`, `isError`) and usage; `usage` has the totals. `allow` is checked again before each model call that follows tool calls, and once a tool has run Inferlo does not fall back to another model (IL5006). New codes: IL5009 (tools outside a route handler), IL5010 (step limit reached), IL5011 (tool is not a registered route). `Message` has optional `toolCalls`, `toolCallId` and `isError` fields and a `"tool"` role, `ProviderRequest` has `tools`, and `mockProvider` can return `{ toolCalls }`. New types: `ToolCall`, `ToolSpec`, `ToolCallResult`, `Step`, `MockReply`.
- `inferlo db migrate --allow-change` now also generates column type changes, for example `t.string().max(120)` to `.max(200)`, `t.text()` to `t.int()` or `t.int()` to `t.number()`: `ALTER TABLE "posts" ALTER COLUMN "title" TYPE varchar(200)`, with a strict `USING` clause when Postgres needs one (other types go through their text, jsonb through its JSON text, and a field becoming `t.json()` through `to_jsonb`). A fixed default is dropped before the change and set again after it. Without the flag these changes are refused with IL4019 (they were IL4013). Values are never cut, rounded or set to NULL: if `--apply` finds one that does not convert, it fails with the new code IL4022, naming the columns and the value, and nothing from that migration is kept. IL4013 now only covers renames, reference and index changes.
- `inferlo db migrate --allow-change` now also generates enum value changes: adding or removing values of a `t.enum` field, or turning a text field into an enum or back, replaces the column's CHECK constraint (`ALTER TABLE ... DROP CONSTRAINT "posts_kind_check"`, then `ADD CONSTRAINT "posts_kind_check" CHECK (...)`, with the name Postgres gave it). Without the flag these changes are refused with IL4019 (they were IL4013). If `--apply` finds rows that still use a removed value, it fails with the new code IL4021, naming the table and constraint, and nothing from that migration is kept.
- CI also tests Node.js 26, the newest LTS line.
- Docs: the framework and app AGENTS.md files now say error codes are `ILxxxx` (they still said `KRxxxx`).

## 0.3.0 - 2026-11-02

- **Breaking: Kairo is now Inferlo.** The npm package is `@browserlessapi/inferlo` (was `@browserlessapi/kairo`), the CLI is `inferlo` (was `kairo`), the GitHub repository is `BrowserlessAPI/Inferlo`, and error codes start with `IL` instead of `KR` (same numbers: KR1001 is now IL1001). `KairoError` is now `InferloError`, `KAIRO_VERSION` is `INFERLO_VERSION`, and `describe()` reports the version as `inferlo`. Environment variables for tests and the benchmark start with `INFERLO_`. To upgrade, replace the package name in imports and package.json, `kairo` with `inferlo` in scripts, and `KR` with `IL` where you match error codes.
- Existing projects keep working: `inferlo db migrate --apply` renames an existing `kairo_migrations` table to `inferlo_migrations` (history is kept), snapshots with the old `"kairo"` key are read, and the `"kairo"` section in package.json is still read for `entry` and `server`.

- Breaking: the minimum supported Bun version is now 1.3.0. Bun 1.2 releases skip or misorder `node:test` subtests, so Inferlo's test suite cannot verify them.

- CI tests every supported version at both ends: Node.js 22.18, 22, 24 and current; Bun 1.3.0 and latest; PostgreSQL 14 to 18 and latest; TypeScript 5.9 and latest. A weekly run catches new upstream releases.

- `inferlo db migrate --allow-change` generates default and required/optional changes of existing columns (`ALTER COLUMN ... SET DEFAULT`, `DROP DEFAULT`, `SET NOT NULL`, `DROP NOT NULL`). Making a column required with a fixed default first fills NULL rows with it. Without the flag these changes are refused with the new code IL4019 (they were IL4013) and nothing is written. If `--apply` hits NULL rows in a column made required, it fails with the new code IL4020, naming the table and column. Also available as `planMigration(models, snapshot, { allowChange: true })`; the plan now includes `changes`, and `--json` output has a `changes` list. IL4013 now covers type, enum value, reference and index changes.
- `migrations/snapshot.json` now describes each column as a structured object (`{ type, notNull, default?, enum?, references?, primaryKey? }`, format `"inferlo": 2`) instead of its SQL text. Snapshots written by 0.2.0 (`"inferlo": 1`) are read and upgraded automatically, and saved in the new format with the next generated migration. IL4013 now says what changed in each column (for example `change column posts.title (type varchar(120) -> varchar(200))`) and lists it in `details.columns`. Types: `MigrationSnapshot` is the new format; `MigrationSnapshotV1` (the old one) and `MigrationSnapshotColumn` are new exports, and `planMigration` accepts either format.
- `inferlo db migrate --apply` records a SHA-256 checksum of each migration file in `inferlo_migrations` and warns with the new code IL4018 when a file that was already applied has been edited since (it is not run again; pending files are still applied). `--json` output has a new `edited` list, and `applyMigrations(db, migrations, { onEdited })` reports the names. Line ending changes do not count as edits. Existing `inferlo_migrations` tables get a `checksum` column automatically, filled from the current files on the next run.
- `inferlo db migrate --allow-drop` generates drops of removed tables, columns and indexes (`DROP TABLE`, `ALTER TABLE ... DROP COLUMN`, `DROP INDEX`, never `CASCADE`), with a warning comment in the file. Without the flag, drops are refused with the new code IL4017 and nothing is written. Also available as `planMigration(models, snapshot, { allowDrop: true })`; the plan now includes `drops`, and `--json` output has a `drops` list. IL4013 now only covers column and index changes.
- Docs: Inferlo is now described as "the TypeScript backend framework with built-in AI model support", with a new "AI models built in" section in the README.
